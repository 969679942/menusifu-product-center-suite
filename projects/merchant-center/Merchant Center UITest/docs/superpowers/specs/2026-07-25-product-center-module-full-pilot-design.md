# 商品中心模块级用例验收试点设计

## 目标

在现有 P0.5、P0.6、P0.7 门禁上增加可分批执行的 `module-full` 范围，并以商品分类 `/pp/brand/category` 打通“测试方案审计、TestCase IR、覆盖验收、Recipe 对齐、UI 执行、API 清理”闭环。

## 范围模型

- `case-only`：审计当前批次质量，不因范围外缺口阻断，兼容存量 `sourceIds` 覆盖。
- `module-full`：必须指定模块，可选指定模块内路由；只审计目标分母，缺口必须为零。
- `full`：审计全部分母，缺口必须为零。
- `module-full` 和 `full` 只认显式 `coverageIds`，禁止用宽泛 `sourceIds` 推导覆盖。

## 覆盖分母

原始 UI 审计可能把同一控件的父子 DOM、不同数据行实例记录为多项。新增机器维护的覆盖归并合同，将多个原始来源 ID 收敛为一个稳定能力 ID，并保留全部来源用于追溯。

商品分类路由归并为七项：页面路由、展开分类、行操作、添加子分类、新增根分类、行操作弹层、分类名称必填校验。

## 试点用例

- 复用现有六条已晋级 Recipe：创建、编辑、删除、必填、100 字符边界、取消删除。
- 从 `商品管理/1.商品中心-商品管理-商品-正式测试用例.md` 导入 `TC-ITEM-STD-035`。
- `TC-ITEM-STD-035` 覆盖“添加子分类”，但当前无稳定自动化能力，保留为 `manual`，不得猜测脚本。
- 为该正式用例向统一合同增加有来源的业务规则记录，不把页面控件证据冒充业务规则证据。

## 数据流

统一合同与覆盖归并合同生成分母，Recipe 生成显式覆盖 ID，TestCase IR 继承覆盖 ID。分类试点构建器生成输入、来源绑定和审计报告，`module-full` 对 `brand-item + /pp/brand/category` 验收。通过后仅运行六条自动化 Recipe；人工用例不编译。

## 验收

- 分类稳定覆盖分母为 7，覆盖 7，缺口 0，未知覆盖 ID 0。
- 七条用例语义审计通过；六条 `executable`，一条 `manual`。
- 六条 UI Recipe 通过，变更场景均执行 API/UI 终态验证与 API 清理。
- TypeScript、统一合同、Recipe 合同、敏感信息和完整生产合同聚合通过。
