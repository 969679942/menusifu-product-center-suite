# ADR-001：执行结果与发布变化观测分离

## 状态

已接受，适用于所有测试方案和系统类型。

## 问题

SaaS、Tomcat + WAR、容器、多节点和第三方系统能够提供的发布标识不同。把固定应用版本设为 `passed` 的必要条件，会把“无法识别发布版本”错误解释为“本次测试没有通过”，并使历史 Allure 结果因日期或会话变化被错误作废。

## 决策

- 本次执行是否通过只由用例指纹、执行上下文、断言覆盖、操作收据和清理证据决定。
- 发布身份属于变化观测，只决定自动复用和当前性声明，不决定本次通过。
- 发布变化观测允许为 `verified`、`derived` 或 `unavailable`。
- 无发布身份但证据完整的通过记录使用 `reuseStatus=run-only`，历史事实永久保留。
- 日期、对话框、工具重启和报告查看时间不是失效条件。
- 可信发布身份发生变化时，只重新验证影响映射覆盖的用例。
- 请求 ID、链路 ID、CDN 节点、响应时间和响应长度不得作为发布身份。

## 系统适配

- SaaS 优先使用发布流水线、部署事件、可信响应头或稳定资源指纹。
- Tomcat + WAR 优先使用部署 WAR SHA-256、构建清单或版本接口，并将 Tomcat、配置和节点身份分开记录。
- 完全无发布信号时不要求测试人员逐条输入版本，也不自动全量重跑。

## 兼容与迁移

- 旧 `applicationVersionFingerprint` 作为历史兼容字段读取。
- 旧账本记录不删除；缺少完整标准收据的记录标记为 `legacy-unverified`。
- 新账本以 `caseId + caseFingerprint + runId` 保存每次运行，避免不同日期或批次互相覆盖。
