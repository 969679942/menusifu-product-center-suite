# 参考系统上下文参数缺失分析与解决方案

生成时间：2026-08-30（Asia/Shanghai）  
问题范围：`public-core` 参考系统脚手架；Merchant Center 业务结果不受本问题直接影响。  
当前状态：已修复并通过参考系统新运行验证；历史失败仍保留为 `automation-gap`，未分类为产品失败。

## 1. 问题摘要

本次公共参考系统验证在 `CASE-SMOKE-001` 的上下文守卫阶段失败：

```text
Expected: "en-US"
Received: undefined
```

失败发生在执行阶段的 `verifyContext`，不是页面访问失败、业务断言失败或产品行为偏差。诊断报告已将其归类为 `automation-gap`，并要求 `inspect-automation`。

## 2. 证据与影响

### 直接证据

- 失败运行报告：`Merchant Center UITest/output/system-test/reference-system/reference-1788025967413/run-report.json`
- 失败诊断：`Merchant Center UITest/output/system-test/reference-system/reference-1788025967413/diagnostics.json`
- 参考脚手架生成器：`Test Automation Platform/scripts/scaffold-system-test.ts`
- 上下文执行器：`Test Automation Platform/src/automation/system-test/system-test-recipe-executor.ts`
- 计划编译器：`Test Automation Platform/src/automation/system-test/system-test-plan-compiler.ts`

### 影响范围

| 对象 | 影响 | 结论 |
| --- | --- | --- |
| 参考系统 Smoke Case | 无法完成上下文守卫，标准收据不完整 | 参考基线暂不可用 |
| 公共平台通用性验收 | 参考系统试点失败 | 平台最终目标仍未完成 |
| Merchant Center 业务用例 | 未执行、无业务失败证据 | 既有结果不失效、不重跑 |
| Merchant Center 产品缺陷 | 没有稳定 UI/API 产品状态证据 | 不得登记产品缺陷 |
| 执行器状态机 | 行为符合合同，拒绝缺失上下文 | 不建议通过默认值修补 |

## 3. 根因定位

### 3.1 计划层有上下文

脚手架在 `test-plan.json` 中声明了完整的 `executionContext`：

```text
environmentId = scaffold-local
locale = en-US
roleId = public-session
tenantScope = public
```

治理策略也要求检查 `route`、`locale`、`role`、`tenant` 和 `business-identity`。

### 3.2 Recipe 层丢失上下文

同一个脚手架在生成 Recipe 时只写入：

```text
contextGuards: [{ input: { phase: before-action } },
                { input: { phase: before-assertion } }]
```

缺少：

```text
expectedRoute
expectedLocale
expectedRoleId
expectedTenantScope
businessIdentityStrategy
```

因此运行器将 Recipe 输入原样解析后传给 `verifyContext`，`expectedLocale` 自然为 `undefined`。

### 3.3 编译器已有正确实现，但参考脚手架绕过了它

公共计划编译器会根据计划上下文生成以下字段：

```text
expectedRoute = item.route
expectedLocale = plan.executionContext.locale
expectedRoleId = plan.executionContext.roleId
expectedTenantScope = plan.executionContext.tenantScope
```

但参考系统验证路径由 `scaffoldSystemTest()` 直接写出 `recipes.json`，没有经过同一套计划编译逻辑。因此产生了两条生成链：

```text
正式系统：test-plan → compileSystemTestPlan → Recipe（有上下文）
参考系统：scaffoldSystemTest → Recipe（缺上下文）
```

这属于生成链路不一致，不是执行器缺少容错。

### 3.4 执行通过但标准证据仍不完整

上下文缺口修复后，参考系统的 setup、preflight 和业务页面均通过，但运行器仍返回 `exit=3`。新报告显示：

- 两个上下文守卫收据已存在；
- 断言回调执行成功，但脚手架未启用 `reportStep`，原执行器只在可选 reporter 的 evidence 回调中生成 Claim 收据；
- 只读根页面实际执行了 `GET` 导航，但脚手架未写入操作收据；
- 公共证据评估因此将结果归类为 `automation-gap`，而不是产品失败。

该问题说明“Playwright 通过”不能替代“标准运行收据完整”。

## 4. 解决方案

### 方案 A：修复参考脚手架 Recipe 生成（必须）

目的：让参考系统生成的 Recipe 与正式系统编译后的上下文守卫合同一致。

实施内容：

1. 在构造 `recipe.contextGuards` 时注入 `testPlan.executionContext`。
2. 为两个阶段都写入 `expectedRoute: '/'`。
3. 写入 `expectedLocale`、`expectedRoleId`、`expectedTenantScope`。
4. 保留 `businessIdentityStrategy: 'none'`，与根页面只读用例语义一致。
5. 生成后重新计算 Recipe collection fingerprint 和 manifest 相关指纹。

预期结果：参考系统两个上下文守卫阶段都能收到完整输入，执行进入页面断言和收据生成阶段。

后续影响：只影响公共参考脚手架和参考系统测试产物；不修改 Merchant Center 正式用例、业务规则、运行账本或历史通过结果。

### 方案 B：统一计划到 Recipe 的生成入口（必须）

目的：消除正式系统和参考系统各自拼装 Recipe 的分叉，防止字段继续漂移。

实施内容：

1. 抽取公共的“计划上下文守卫生成器”。
2. `compileSystemTestPlan()` 和 `scaffoldSystemTest()` 都调用该生成器。
3. 生成器以 `SystemTestPlan.executionContext` 为唯一来源。
4. 禁止调用方手写 `expectedLocale`、`expectedRoleId` 和 `expectedTenantScope` 默认值。
5. 当计划声明必检项而 Recipe 缺字段时，在生成阶段直接返回结构化错误，不等到浏览器运行时才失败。

预期结果：所有系统接入，包括未来不同 `applicationId` 的系统，都使用同一上下文字段映射。

后续影响：属于 `public-core` 生成能力变更，必须补公共合同和系统无关负向测试；不能只在 Merchant Center 适配器中修补。

### 方案 C：补充生成前合同门禁（必须）

目的：在认证、造数和页面动作之前发现计划/Recipe 上下文断裂。

至少校验：

- 每个 `contextGuard` 都有 `phase`。
- 每个治理要求的 `route`、`locale`、`role`、`tenant` 都有对应输入。
- `expectedLocale === plan.executionContext.locale`。
- `expectedRoleId === plan.executionContext.roleId`。
- `expectedTenantScope === plan.executionContext.tenantScope`。
- `expectedRoute` 与 case route 及 route match 合同一致。
- Recipe collection fingerprint 与 manifest 来源指纹一致。

预期结果：缺失字段在静态编译阶段被分类为 `automation-gap`，不会启动认证、造数或浏览器。

### 方案 D：增加参考基线回归和负向合同测试（必须）

正向测试：

1. 脚手架生成的 `test-plan.json`、`recipes.json` 和 `manifest.json` 上下文一致。
2. `before-action` 和 `before-assertion` 均收到完整上下文。
3. 根页面只读断言通过。
4. 生成标准上下文守卫收据和执行报告。

负向测试：

1. 删除 `expectedLocale` 时，生成/编译阶段阻断。
2. 修改 Recipe locale 与计划 locale 不一致时，阻断执行。
3. 删除 `expectedRoleId` 或 `expectedTenantScope` 时，阻断执行。
4. 修改 route 时，断言前守卫阻断。
5. 参考系统上下文失败不能被归类为 `product-failure`。

验收命令应覆盖：

```powershell
npm --prefix "D:\Menusifu\Test Automation Platform" run test:acceptance
npm run verify:system-test-reference
```

其中第二条命令必须在修复后通过；如果仍失败，应保留新的 runId、诊断和检查点，不得复用本次失败收据。

## 5. 不推荐方案

### 暂不建议：执行器自动填充默认值

不建议在 `executeSystemTestRecipe()` 或公共 `resolveSystemTestRecipeInput()` 中把缺失的语言、角色、租户默认成 `en-US`、`public-session` 或 `public`。

原因：

- 会掩盖计划到 Recipe 的生成缺口。
- 不同系统、租户和语言可能被错误地执行。
- 上下文守卫会变成“看似通过但验证了错误上下文”。
- 违反“不猜测上下文”的证据合同。

### 暂不建议：修改 Merchant Center 业务适配器兜底

本次失败发生在 `reference-system`，不是 Merchant Center 的 `zh-CN`、`merchant-operator` 或 `configured-merchant` 适配器。修改 Merchant Center 适配器不能修复公共参考基线，还会模糊公共层与项目层边界。

### 暂不建议：重跑 Merchant Center 业务用例

本次没有 Merchant Center 业务执行、产品状态或当前用例指纹变化。为验证公共参考基线而重跑 Merchant Center 业务用例没有证据收益，已有结果保持不变。

## 6. 实施顺序

```text
修复 scaffold Recipe 上下文
→ 抽取公共上下文守卫生成器
→ 增加生成前字段一致性门禁
→ 使断言收据独立于可选 reporter
→ 为只读导航补齐操作收据
→ 增加正向/负向公共合同测试
→ 通过公共 acceptance
→ 重新运行 reference-system
→ 生成新的标准收据
→ 更新平台检查点
```

停止条件：

- 任一必需上下文字段缺失时，静态门禁必须先阻断。
- 参考系统通过前，不得声明公共平台完成。
- 参考系统失败不能改变 Merchant Center 模块交付状态。
- 修复后只能使用新的 `runId` 和新的实现指纹验证，不能修改旧失败报告。

## 7. 已执行变更与验收结果

本次实施范围为 `public-core + generated-evidence`，未修改 Merchant Center 领域适配器，未执行 Merchant Center 业务写操作或历史业务用例重跑。

已实施：

- `scaffold-system-test.ts` 使用独立的 `executionContext`，避免初始化顺序错误，并把完整上下文写入两个守卫；
- 计划编译器和脚手架共用上下文守卫生成器，并增加上下文输入一致性验证；
- 公共执行器在动作成功后独立生成断言收据，不再依赖可选报告器；
- 参考脚手架记录只读 `GET` 导航操作收据；
- 增加脚手架上下文正向/负向合同测试，以及无 reporter 断言收据合同测试。

验收结果：

- `npm run typecheck`：通过；
- `npm run test:acceptance`：`13/13` 通过；
- 公共平台合同测试：`68/68` 通过；流程、运行时合同及平台合同组合测试：`99/99` 通过；
