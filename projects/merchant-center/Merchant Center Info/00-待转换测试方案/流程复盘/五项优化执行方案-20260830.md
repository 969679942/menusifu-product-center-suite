## 1. 执行目标

将当前测试流程从“能够生成和运行用例”提升为“资产分母一致、审计持续新鲜、环境能力可判定、执行风险可度量”的闭环：

```text
权威资产与分类
→ 审计观测与新鲜度
→ 事件/定时触发
→ 能力匹配与执行选择
→ 风险排序与稳定性度量
→ 标准收据、状态裁决和派生产物
```

成熟实践对齐原则：

- 以单一事实来源和可重复构建解决测试资产漂移；
- 以事件驱动加定时兜底解决审计滞后；
- 以环境能力注册和执行前门禁解决运行到中途才发现不可用；
- 以风险分层和 Flaky 指标控制回归成本，而不是无差别全量执行；
- 以当前 `caseId`、用例指纹、上下文指纹和标准收据作为唯一结果依据。

## 5. 阶段 1：统一资产分母和生命周期派生产物（必须）

### 目的

### 执行方案

1. 先修改公共生命周期和项目适配器合同，使分母由权威 case 集合及分类状态计算；`expectedLanded`、`expectedExclusionsByStatus` 等字段不得再作为当前完成判定输入。
2. 以正式用例正文、已完成索引、未落地索引和统一业务决策为输入，重新生成资产分类。
3. 由公共生命周期命令派生 `remediation-scope`，并区分计算值与历史诊断值。
4. 按 `caseId` 做集合对账：
   - 正式用例是否唯一；
   - 已完成/未落地是否重复；
   - 绑定是否有正式用例；
   - 延期和不适用是否有原因及恢复条件；
   - 产品偏差是否有责任闭环。
5. 增加负向合同：静态预期数量与当前集合不一致时必须报 `COUNT_SOURCE_STALE` 或等价诊断，不能修改预期数字掩盖差异。
6. 依次重建 readiness、review queue、final verdict 和平台外部依赖派生状态。
7. 为每个派生产物写入输入指纹、生成时间、来源路径和分类统计。
8. 若发现集合变化，先登记差异，再决定是否改变用例分类。

### 关键不变量

```text
planned = executionEligible + classifiedExclusions
executionEligible = executed
executed = passed + failed
```

延期、不适用、来源阻断、技术阻断和产品偏差必须逐条占据分类分母，不能被隐藏在“未落地”总数中。

### 预期结果

- 适配器不再承担手工总数真相；
- 当前 `420 + 188 + 16 = 624` 能被所有派生产物一致复算，或输出明确差异；
- 旧的 `421/194/9` 仅作为历史诊断保留，不再作为当前门禁输入；
- 生成过程幂等，输入不变时重复生成结果指纹不变。

### 验收与回滚

- 必须通过资产索引、remediation scope、生命周期、平台评审和最终裁决合同测试。
- 若集合对账失败，停止后续发布，保留旧派生产物为历史，不覆盖当前有效结果。
- 回滚只回滚本次生成的派生产物，不回滚正式用例、历史执行账本和业务结果。

## 6. 阶段 2：重新生成商品中心审计并补齐新鲜度（必须）

### 目的

解决审计页面信息滞后、上下文缺失和旧报告继续被消费的问题，建立“报告可用期限”和“运行上下文匹配”双重门禁。

### 执行方案

1. 先读取阶段 1 的最新计划和受影响 `caseId`，按模块和执行上下文分组。
2. 执行真实只读观测命令，而不是只执行规则审计：
   - `npm run observe:product-center:page-contract`：页面路由、控件、字段、弹窗和可访问性合同；
   - `npm run observe:product-center:api`：关键网络/API 方法、路径、状态和 operation 映射；
   - `npm run audit:product-center:item-control-drift`：控件漂移和 locator 影响；
   - `npm run build:product-center:audit-report`：汇总当前观测、结构化 Diff 和可消费报告。
3. 再执行 `audit:test-plan:closure`、`flow:test-plan:evidence-closure` 和历史证据协调；这些命令不能替代页面/API Probe。
4. 审计开始前写入 `audit.started`，结束后写入 `audit.completed`；异常时写入失败 checkpoint，不发布半成品。
5. 审计文档必须写入：
   - `generatedAt`：文档生成时间；
   - `observedAt`：页面/API 实际观测时间；
   - `freshUntil`：按风险策略计算的失效时间；
   - `applicationVersionFingerprint`；
   - `environmentId`、`tenantScope`、`roleId`、`locale`；
   - 页面结构指纹、网络/API 指纹、来源指纹和审计实现指纹；
   - 逐 `caseId` 的审计状态、Diff、证据引用和缺失项。
6. 将结构变化分类为 `clean-diff`、`technical-drift`、`source-drift` 或 `unknown`。
7. 只有 `fresh`、上下文匹配、来源完整且 Diff 可解释的记录才能进入用例生成和执行候选。
8. 对当前历史报告执行一次转换检查：缺少必需字段的旧报告只能进入历史协调或重审，不得直接覆盖为当前有效审计。
9. 若真实观测因认证、环境或外部依赖失败，记录为 `environment-blocked` 或 `technical-blocked`，不得用规则审计成功替代页面观测成功。

### 新鲜度策略

| 风险 | 示例 | 建议 TTL | 触发方式 |
| --- | --- | --- | --- |
| 高 | 登录、权限、商品创建/修改/删除、清理链路 | 1 天或版本变更即失效 | 事件 + 每日兜底 |
| 中 | 核心商品详情、组装、规格和状态流转 | 3 天 | 事件 + 每 3 天兜底 |
| 低 | 稳定只读列表和辅助页面 | 7 天 | 事件 + 每周兜底 |

TTL 只是候选默认值，最终按实际发布频率和风险评估调整；任何 `freshUntil` 缺失、非法或上下文缺失均为 `invalid`，不能按无限期有效处理。

### 预期结果

- 形成当前商品中心审计报告、证据清单、结构化 Diff 和新鲜度状态；
- 审计页面信息能够被 `flow` 在执行前判断为 `fresh` 或明确阻断；
- 过期或上下文漂移只影响对应 `caseId`，不扩大为无依据的全量重跑。

### 验收与回滚

- 必须验证 `observedAt`、`freshUntil`、环境、角色、语言、版本和页面/API 指纹均非空且可解析。
- 必须验证过期、角色变化、语言变化、版本变化和来源变化会触发重审。
- 审计失败不得覆盖上一份完整历史报告；`latest` 指针只允许原子切换到完整产物。
- 审计只读 Probe 不产生业务对象；若发现写入或残留，按异常停止并转清理核查。

### 后续影响

- 级别：必须；范围：`public-core + project-adapter + generated-evidence`。
- 既有通过结果：不因重新生成审计自动变为失败；仅在语义、绑定、上下文或产品观测变化时进入重验证。
- 成本：增加只读 Probe 时间和存储；换取旧定位器、字段和接口信息不再长期误导执行。

## 7. 阶段 3：增加审计定时兜底和发布/配置变更触发（必须）

### 目的

解决仅在测试流程启动时才发现审计过期的问题，使审计既能被变更即时触发，又能在事件丢失时自动恢复。

### 执行方案

#### 3.1 事件触发

先建立公共事件合同和项目触发适配器，再接入发布系统或配置中心。对应合同测试必须先于调度上线。

统一审计触发事件至少支持：

- 应用发布或版本指纹变化；
- 路由、字段、权限、功能开关或 API 合同变化；
- 正式用例、来源、绑定、执行上下文或清理适配器变化；
- 审计报告进入 `stale`、`invalid` 或 `unknown`；
- 失败恢复条件满足。

事件必须包含：`eventId`、`eventType`、`applicationId`、`planId`、影响范围、来源指纹、幂等键、创建时间、审计优先级、owner、SLA 和保留期限。

#### 3.2 定时兜底

1. 每日扫描高风险审计，每 3 日扫描中风险审计，每周扫描低风险审计。
2. 定时任务只生成待审计队列，不直接启动 Merchant Center 业务用例。
3. 使用 `applicationId + planId + caseId/route + contextFingerprint + reason` 去重。
4. 失败任务保留 checkpoint，按 5、15、30、60 秒有限退避；超过上限转人工/技术队列。
5. 事件恢复后先查询幂等键和任务状态，不盲目重复创建任务。
6. 为任务设置 owner、SLA、告警阈值和升级路径；积压、连续失败和高风险审计过期必须告警。

#### 3.3 结果消费

- 审计任务成功：原子发布新报告并更新 `freshUntil`；
- 审计任务失败：保留旧报告为历史，当前消费状态变为 `stale` 或 `invalid`；
- 事件积压：报告页面显示待处理数、最老事件时间和 SLA；
- 同一原因重复触发：合并为一次审计，保留所有来源事件引用。
- 超过 SLA：自动升级到指定负责人；超过保留期限的事件归档但不得删除结论链。

### 预期结果

- 变更发生后能在 SLA 内生成审计任务；
- 事件丢失时由定时任务发现过期并补触发；
- 重复事件不会造成重复 Probe 或重复业务执行；
- 审计页面明确显示最后观测时间、失效时间和当前状态。

### 验收与回滚

- 必须测试事件去重、事件乱序、事件重复、任务超时、任务中断和恢复。
- 必须测试定时任务与事件任务并发时只产生一个有效审计执行。
- 必须测试审计任务失败不覆盖有效历史，不自动降级为全量业务回归。
- 必须测试事件 schema、权限、owner/SLA、积压告警和保留策略。
- 回滚时可暂停调度器，但不能删除事件和 checkpoint；恢复后从未完成任务继续。

### 后续影响

- 级别：必须；范围：`public-core + project-adapter`，调度配置属于项目配置。
- 既有通过结果：不改变；只影响审计状态和未来增量候选。
- 成本：增加调度、事件存储和告警维护成本；显著降低审计过期静默存在时间。

## 8. 阶段 4：环境能力注册与执行前能力匹配（必须）

### 目的

解决用例已经启动、认证后才发现 POS、终端、下发、渠道终态或清理能力不存在的问题，将环境不适用性前移到执行选择阶段。

### 执行方案

1. 先在公共平台定义环境能力注册 schema 和匹配合同，再在项目适配器中建立商品中心能力注册模型。建议项目产物为 `environment-capability-registry.json`，每项能力必须关联验证收据。
2. 在项目适配器中建立环境能力注册模型，至少包括：
   - `environmentId`、`applicationId`、`tenantScope`、`roleId`、`locale`；
   - 登录和上下文能力；
   - UI/API 观测能力；
   - 数据创建、服务端身份查询和清理能力；
   - POS、终端、渠道下发、模板、门店和下游终态能力；
   - 能力版本、有效期、负责人和验证收据。
3. 为每条用例声明 `requiredCapabilities`、`forbiddenCapabilities`、最低版本和能力失效条件。
4. 执行前将用例需求与当前环境能力做精确匹配：
   - 全部满足：进入 `executionEligible`；
   - 缺少外部能力且已确认：进入 `deferred`；
   - 配置/绑定缺失：进入 `blocked-technical`；
   - 来源明确废弃或业务不适用：进入 `not-applicable`；
   - 只有稳定 UI/API 终态证据证明预期错误时，才进入 `product-defect`。
5. 匹配结果写入执行选择、checkpoint 和运行收据，不能只停留在日志中。
6. 能力变化按影响图映射到受影响 `caseId`，触发审计或重验证，不默认全量执行。

### 预期结果

- 浏览器启动前即可知道每条用例是否具备执行条件；
- 当前已确认延期用例保留正式方案和恢复条件，不进入 fixture、造数或 Playwright 注册；
- 环境阻断不再误报为产品失败；
- 能力注册可以被其他系统复用，而不是只服务商品中心。

### 验收与回滚

- 必须验证缺能力、能力过期、能力版本不匹配、租户不匹配和角色不匹配均在浏览器前阻断。
- 必须验证能力齐全时只选择对应 `caseId`，不扩大选择集。
- 必须验证能力变化会产生稳定的影响 `caseId` 集合。
- 必须验证能力注册本身有来源或验证收据，不能凭人工描述直接标记可用。
- 必须验证能力注册文件、执行计划、fixture 注册和运行收据使用同一能力快照指纹。
- 回滚时保留旧能力快照，已生成的执行选择按指纹失效，不继续消费过期选择。

### 后续影响

- 级别：必须；范围：`project-adapter + public-core contract`。
- 既有通过结果：不失效；只影响下一轮执行前筛选和延期/技术阻断分类。
- 人工投入：首次建立能力矩阵需要业务、环境和研发共同确认；后续由验证收据维护。
- 平台复用：可为未来不同 `applicationId` 试点提供统一接入合同。

## 9. 阶段 5：风险分层和 Flaky Test 指标（可选）

### 目的

在不改变通过裁决的前提下，用风险和稳定性指标优化审计频率、Canary 选择、批次顺序和人工处理优先级。

### 执行方案

#### 9.1 风险分层

为每条用例计算可解释的风险等级，输入至少包括：

- 业务重要性和数据破坏风险；
- 变更影响范围和下游依赖数量；
- 权限、租户和合规敏感度；
- 历史失败、环境失败和清理残留记录；
- 断言通道数量和外部能力数量。

输出 `critical/high/medium/low` 及评分原因，不能只输出不可解释的黑盒分数。

风险等级只用于：审计 TTL、执行优先级、Canary 样本、人工确认优先级和告警阈值；不能直接把用例判为通过或失败。

#### 9.2 Flaky 指标

按 `applicationId + caseId + caseFingerprint + implementationFingerprint + contextFingerprint` 统计：

- 最近 30 次成功率；
- 首次失败率；
- 重试后通过率；
- 环境失败率、超时率、定位失败率；
- 产品失败率；
- 清理残留率；
- 平均恢复时长和隔离时长。

建议状态流转：

```text
正常
→ 观察
→ flaky-suspected
→ quarantined
→ 修复验证
→ 恢复主回归
```

“重试后通过”必须保留首次失败事实，不能直接当作稳定通过；隔离用例仍需保留来源、责任人、恢复条件和 SLA。

当前 `audit:product-center:maintainability` 只能作为维护性补充检查，不等价于风险或 Flaky 指标。必须先实现独立指标命令、数据 schema 和合同测试，再启用本阶段；在此之前本阶段保持 `可选/未启用`。

### 预期结果

- 获得风险排序、稳定性趋势和可解释的隔离建议；
- 高风险且高变更用例优先审计和执行；
- Flaky 用例不会通过无限重试掩盖真实质量问题；
- 不改变当前标准收据和状态裁决。

### 验收与回滚

- 必须验证指标按指纹隔离，不能把不同版本或不同环境混为一谈。
- 必须验证瞬时平台失败不被统计为产品失败。
- 必须验证低样本量时标记 `insufficient-sample`，不做强结论。
- 必须验证风险评分变化不会擅自扩大执行选择集。
- 回滚时只停止排序和告警消费，不删除历史运行账本。

### 后续影响

- 级别：可选；范围：`public-core + generated-evidence`。
- 既有通过结果：不失效、不重跑。
- 成本：增加指标存储、报表和治理维护；短期内可能增加人工复核，但会降低长期误重跑成本。

## 12. 完成判定

1. 资产分母和所有生命周期派生产物从同一权威输入派生且无差异；
2. 当前商品中心审计具备完整新鲜度和上下文证据，旧报告不可直接消费；

5. 风险和 Flaky 指标可解释、按指纹隔离且不改变证据裁决；
6. 公共合同、项目适配器合同、敏感信息扫描和回滚演练均通过；
7. Merchant Center 业务结果仅在明确批准并取得当前标准收据后更新；
8. 不同 `applicationId` 的真实系统试点仍需单独授权，不能用本方案完成声明替代平台最终目标门禁。

## 13. 结果影响声明

- `public-core`：会增加通用合同、调度、能力匹配和度量能力；不改变产品业务规则。
- `project-adapter`：会补充商品中心环境能力、审计上下文和生命周期输入映射；不复制公共状态机。
- `domain-asset`：只更新权威资产引用、分类差异和责任闭环；不删除历史用例。
- `generated-evidence`：会生成新的索引、审计、checkpoint、readiness 和评审产物；旧产物保留为历史并按指纹判断是否可消费。
- 已有业务通过结果：默认不重跑、不失效；只有当前用例、绑定、上下文或产品观测发生实质变化时，才进入受影响用例的显式重验证。
- 跨系统平台状态：继续保持 `deferred/incomplete`，直到获得不同 `applicationId` 的真实目标系统及完整试点收据。
