# 测试平台最终目标

## 最终目标

建立一套可供任何测试方案复用的、由 AI 驱动但受证据和门禁约束的测试全流程：

```text
需求与审计来源
→ 正式测试用例
→ 自动化绑定与脚本
→ 增量执行
→ UI/API/下游/清理证据
→ 运行账本与状态裁决
→ 资产索引与 CI 门禁
```

流程必须减少非必要人工审核，同时不得通过猜测字段、控件、提示、接口或业务规则来替代证据。

## 通用化原则

- 跨测试方案、跨业务系统复用是所有后续流程优化的默认验收目标，无需用户在新对话中重复提出。
- 证据权限、用例状态机、变更指纹、执行选择、运行账本、通过判定和索引生成必须建设在公共平台层。
- 商品、组、分类等模块差异只能放在模块适配器、页面对象、业务合同和数据工厂中。
- 模块专用脚本或合同只能证明该模块已接入，不能称为通用流程已经完成。
- 新测试方案接入时，应通过配置和适配器复用公共流程，不得复制一套状态机或门禁。
- 紧急领域修复若暂时无法同步抽取公共能力，必须登记平台缺口并保持“流程未完成”，不得用领域用例通过替代平台验收。

## 平台级强制治理合同

所有新方案和迁移方案必须由统一编译器校验以下合同，缺一项不得注册执行：

1. `semantic contract`：业务对象、场景族、状态转换、作用域、变体及变体独立来源；仅 `caseId` 或标题不同不能证明场景不同。
2. `assertion surface contract`：每个预期绑定字段 ID、权威验证面、观察通道、路由和验证权威；列表摘要不能替代详情或持久化验证。
3. `feedback contract`：精确提示只能来自 UI 审计或运行证据；已提交操作的反馈必须关联对应 operation key，按钮置灰不得伪造提交请求。
4. `context guard contract`：业务动作前和断言前验证路由、语言、角色、租户及适用时的服务端 ID/唯一业务身份，并生成独立守卫收据。
5. `evidence contract`：缺少上下文守卫收据、断言收据、操作收据或要求的清理收据时不得判定完整。
6. `execution grant contract`：正式业务用例只能由统一运行器签发的短期授权启动；授权必须绑定 `applicationId + runId + 精确 caseId 集合`，直接运行 spec、越权 caseId、过期授权或已撤销授权必须在认证、造数和页面动作前失败。

公共实现位于 `D:\Menusifu\Test Automation Platform\`；系统差异只能通过商品中心或其他项目适配器、adapter catalog 和方案治理配置接入。

## 证据与通过规则

- PRD、XMind、正式用例、页面审计、网络请求和运行结果均必须保留来源与指纹。
- 截图或视频可用于人工业务规则确认，但不能单独证明服务端持久化、引用同步、清理终态或自动化通过。
- `passed` 必须来自当前用例指纹和执行上下文下的完整执行收据，并覆盖该用例声明的全部断言面；发布身份缺失不得否定本次执行通过。
- 网络超时、页面不可达、认证失效和自动化缺陷必须与产品失败分开分类。
- 没有来源或审计证据时，不得生成精确字段、精确提示或精确 API 行为。

## 人工确认后的自动闭环

人工确认用于解除业务规则歧义，不替代运行。人工确认造成以下任一变化时，受影响用例必须自动转为 `ready` 并进入增量执行计划：

- 前置条件、测试步骤、预期结果或精确提示变化。
- 页面控件、字段身份、弹窗顺序或断言面变化。
- 自动化绑定、handler、locator、数据工厂、API 映射或清理策略变化。
- 已确认的发布、配置、功能开关、用例指纹或执行上下文变化，使受影响历史结果需要重新验证。

日期、对话框和报告查看时间不属于影响性变化，不得使历史结果失效。只有执行语义或已观测系统变化影响用例时，才进入增量重验。

## 资产与状态要求

- 每个模块只保留一份正式测试用例正文，每条用例拥有唯一 `caseId`。
- 自动化绑定状态、运行状态、产品缺陷和延期状态必须分别记录，不得互相代替。
- 延期用例保留正式用例和恢复条件，不注册执行，也不得删除或标记通过。
- 产品偏差必须经过产品修复或业务规则确认、用例更新和重跑后才能关闭。
- 正式用例、绑定、执行计划、运行账本、已完成索引和未落地索引必须能够按 `caseId` 对账。
- `handlingStatus`、`verificationStatus`、`actionRequired` 必须独立保存；已整改但待旧收据迁移的用例不得重新进入执行候选。
- 批次报告只有在结构化内容逐条包含当前 `caseId` 及其成功结果时才能作为该用例证据；共享文件路径和汇总通过数不能批量授权用例状态。
- 后续旧失败不得覆盖已接受的整改结果；只有用例、实现、上下文或已观测产品变化才能重新把 `actionRequired` 设为真。

## 通用流程验收标准

只有同时满足以下条件，才能声明通用流程完成：

1. 任意新测试方案能够使用同一公共命令完成审计匹配、用例更新、脚本生成、执行、结果聚合和索引刷新。
2. 人工规则变更能够通过用例指纹自动触发受影响用例重跑。
3. 没有执行收据的用例无法进入 `passed`，截图无法绕过该门禁。
4. 选择 N 条用例时只注册 N 条，每批认证不超过一次，单条失败不阻断其他用例。
5. 重复构建结果一致，失败后可以从检查点继续，历史结果无需全目录扫描。
6. 每个创建对象记录服务端 ID，清理后按用例要求验证 UI 与 API 零残留。
7. 公共规则拥有模块无关的自动合同测试；模块合同只验证适配器行为。
8. 平台成熟度使用系统无关的参考基线，并强制满足 `planned = executionEligible + classifiedExclusions`、`executionEligible = executed`、`executed = passed + failed`；不得读取某模块过期运行报告充当平台分母。
9. 每次重建平台评审队列时必须自动复核已有平台发布；候选指纹或治理指纹变化后，旧 `formal` 必须自动降级为 `not-approved`，不得依赖人工发现。
10. 平台晋级必须按 `caseId + 用例指纹` 逐条解析标准执行收据，验证 API/UI 清理和证据文件指纹；任何旧的全局零残留布尔汇总都不能单独授权晋级。
11. 产品缺陷、来源阻断、技术阻断、环境阻断和需重验证必须分开分类，网络超时、认证失败、定位漂移和下游能力缺失不得自动归为产品失败。
12. 平台正式评审必须具备不同 `applicationId` 的真实目标系统试点；同一应用内跨业务域只证明跨方案复用，不能证明跨系统通用。

## AI 执行要求

每次处理测试相关任务前，AI 必须读取本文件和统一入口 `README.md`，然后核对权威用例、状态索引和相关审计证据。实施前判断改动属于：

- 公共平台能力；或
- 模块适配能力。

若需求目标是通用流程，而实现只覆盖单一模块，AI 必须明确说明尚未完成，不能以局部落地替代最终目标。

若当前项目适配器的 `deliverables/system-test-platform/platform-external-dependency.json` 存在，必须将其作为跨对话平台检查点读取。当前商品中心的实际文件为 `D:\Menusifu\Merchant Center\Merchant Center UITest\deliverables\system-test-platform\platform-external-dependency.json`。阻断登记处于 `deferred` 时，恢复条件未满足不得重复运行已冻结模块或已达重试上限的试点；只有新增真实目标系统、认证/适配器修复或其他登记的恢复条件成立时，才允许创建新的定向执行授权。

平台迁移或目录治理任务必须读取当前项目的 `adapters/test-automation-platform/project-adapter.json`、`deliverables/system-test-platform/artifact-manifest.json` 和迁移完整性基线。项目产物身份不匹配、旧公共产物路径回流、必需迁移资产缺失或受管迁移哈希未显式接受时只能输出迁移未完成。迁移收口必须通过项目统一命令重建就绪状态、评审队列和最终裁决；不得以单次文件扫描代替派生状态刷新，也不得因迁移收口重跑已通过业务用例。

项目 readiness、评审队列、最终裁决、外部依赖和迁移报告必须由公共 `run-project-lifecycle.ts` 根据 `project-adapter.json.lifecycle` 生成；项目不得复制同类编排脚本。迁移基线接受必须提供批准人和原因，并生成含前后指纹、增删改清单及哈希链的项目级收据；无批准参数、无匹配收据、收据篡改、新增受管文件未接受或无变化重复接受时必须阻断。

## 推荐决策三问

每次提出或执行“下一步”“建议”“优化方案”前，必须先形成并向用户明确说明：

1. `目的`：解决哪个具体问题，为什么现在需要做。
2. `预期结果`：会得到哪些可核验产物、状态变化或验收结论。
3. `后续影响`：对已有通过结果、重跑范围、人工投入、执行耗时与成本、模块交付，以及跨方案和跨系统复用有什么影响。

推荐必须同时标记为 `必须`、`可选` 或 `暂不建议`。以下任一条件不满足时，只能先调查，不能直接推荐执行：

- 目的具体且与当前缺口直接相关。
- 结果可测量、可验收，并有明确停止条件。
- 影响范围已说明，尤其明确是否会重跑或使历史结果失效。
- 没有把平台成熟度建设误写成当前模块交付阻断。
- 没有重新打开已闭环任务，且采用能取得相同结果的最小动作。

执行完成后必须对照原定三问报告实际结果；出现非预期影响时更新治理记录。该合同跨对话、跨测试方案、跨 SaaS 与传统部署系统持续生效，无需用户重复提出。

## 商业级平台硬门禁

- 每个标准化方案必须提供 `sourceRegistry` 和 `executionContext`；来源 ID 必须能解析到已验证文件指纹、路由、合同 ID 和允许的观察通道。
- 每条预期必须声明观察通道（`ui`、`api`、`downstream`、`cleanup`）、验证权威和稳定终态；UI 预期不得由 API 证据替代。
- 执行收据必须由平台重新计算证据指纹，包含发布变化观测（允许不可用）、环境、语言、角色、路由、断言覆盖、操作收据和 UI/API 清理结果；脚本自报 `complete` 不具备授权能力。
- 超时、认证失效、连接重置、定位漂移、数据工厂冲突、清理残留和外部能力缺失必须分类为技术或环境问题；只有稳定的 UI/API 终态同时证明预期不成立时，才允许进入产品失败。
- “已完成”目录只表示“已绑定自动化脚本”，不表示已经运行通过；执行通过只能来自匹配 `caseId + 用例指纹 + 执行上下文 + 执行批次` 的完整收据。发布身份只控制自动复用和当前性声明。
- 人工规则变化必须进入统一增量执行计划；公共命令必须完成编译、合同校验、增量选择、执行、收据导入、状态裁决和索引刷新，任何中断均从检查点恢复。
- 平台正式发布必须绑定当前候选指纹和治理指纹；权威方案、公共门禁或执行合同变化后，旧发布自动失效。

## 统一命令

标准系统使用：

```text
npm run flow:system-test -- --plan=<plan.json> --manifest=<manifest.json>
npm run flow:system-test -- --plan=<plan.json> --manifest=<manifest.json> --execute
```

平台统一校验使用：

```text
npm run verify:system-test-platform
```

该命令是最终目标严格门禁，不只是代码测试。公共运行实现、当前领域适配器、参考基线、跨方案试点或不同 `applicationId` 的跨系统试点任一缺失时必须以 `FINAL_GOAL_NOT_MET` 非零退出并输出“未完成”；不得把局部合同通过描述为通用流程完成。

平台最终目标门禁与业务模块交付门禁必须隔离。缺少跨应用试点时，平台通用化状态只能是“未完成”，但不得因此阻断或降级已经满足自身来源、绑定、执行、证据、清理和索引门禁的商品中心测试方案。平台裁决必须输出 `scope=platform-universal-completion` 和 `moduleDeliveryBlocked=false`，防止下游把跨系统验证缺口误当成商品中心失败。

不带 `--execute` 只编译并写入检查点，避免整改期间误跑业务；带 `--execute` 才执行受影响用例。

商品中心当前闭环审计使用以下安全链路：

```text
npm run audit:test-plan:closure
→ product-center-closure-audit.json
→ npm run flow:test-plan:evidence-closure
→ product-center-historical-evidence-reconciliation.json
→ 二次闭环审计与新的增量候选
→ 人工或策略明确批准 caseId
→ npm run approve:test-plan:incremental -- --case-ids=<id1,id2> --approved-by=<operator>
→ npm run test:test-plan:approved-incremental
→ npm run test:test-plan:approved-incremental -- --execute
→ 收据导入、状态裁决、索引刷新
```

- 审计命令只生成候选，不会启动页面执行；`approvedCaseIds` 为空是正常的安全初始状态。
- 批准命令只接受当前闭环审计推荐且已进入当前执行计划的 `caseId`，拒绝延期、不可用和已解决用例。
- 增量执行命令校验审计时间戳和候选名单；名单过期或为空时停止，不降级为全量运行。
- 截图和视频只能作为分析参考；没有当前用例指纹和完整执行收据不能进入 `passed`。历史通过永久保留，是否需要重验由明确变化和风险策略决定。
- 当前闭环若显示 `change-revalidation-required` 或 `evidence-revalidation-required`，代表存在明确变化影响或执行证据缺口，不代表业务失败，也不代表可以自动重跑全部用例。
- 当前闭环若显示 `evidence-reconciliation-required`，代表存在历史通过或历史证据引用，必须先自动尝试补录标准收据；补录失败且无法证明完整执行时，才允许转入重跑审批。
- 每次进入重跑审批前必须执行一次证据闭环任务；该任务固定执行前审计、历史证据协调和后审计三阶段，并保存检查点。
- 审计阶段指纹必须动态包含正式用例、来源合同、人工决策、自动化绑定、执行计划、运行账本及所有已登记证据文件；其中任一真实输入变化自动触发重审，日期、对话框和未变化输入不得触发。
- 前审计与后审计必须写入不同中间产物；无输入变化时重复执行闭环命令必须保持检查点和结果不变。
- 历史报告存在但不满足新版收据合同时，先生成旧收据适配任务，不直接重跑页面；只有适配仍不能证明完整执行，才进入显式重跑审批。

## 定向修复效率门禁

- 单条或小批量定向修复必须写入公共修复尝试账本，账本键至少包含 `applicationId + caseId + caseFingerprint + implementationFingerprint`，并跨进程、跨对话复用。
- 所有正式执行必须经统一运行入口签发短期执行授权；领域运行器只能消费授权，不能自行扩展用例范围。授权文件不得保存明文令牌，批次结束必须撤销，防止直接 Playwright 命令绕过审计、增量选择和修复预算。
- 同一实现发生确定性失败后，未改变实现指纹不得再次启动浏览器；瞬时平台失败按恢复策略最多重试 1 次。
- 每个修复轮次最多执行 2 次且最长 15 分钟。达到任一上限后必须先生成结构化诊断记录，包含根因、修正动作和证据引用，才能开启下一轮。
- 同一用例、同一用例指纹最多开启 2 个修复轮次；仍未闭环时停止页面试错并进入技术复核，不得持续消耗运行资源。
- 当前实现已经取得完整通过收据时禁止重复运行。仅文案、报告说明或非执行语义元数据变化，不得触发页面重跑。
- 失败后只执行诊断、局部合同测试和受影响脚本；正式执行计划、闭环审计和全量资产索引只在最终通过或正式分类改变后统一刷新一次。
- 定向运行的认证、数据创建和清理开销必须计入修复预算；不得把多次 Playwright 进程启动时间隐藏在业务用例耗时之外。
- AI 诊断默认只读取当前执行收据、当前失败报告、目标用例、直接绑定的 flow/page/adapter 和对应审计合同；禁止对 `output`、`allure-results`、`test-results` 或历史交付目录做无过滤递归全文扫描。
- 单次检索必须限制目录、文件类型和输出规模；预计超过 5,000 行时必须改用索引、结构化 JSON 查询或精确 `caseId`，不得把海量历史匹配结果送入分析上下文。
- 页面运行前必须先完成类型检查或受影响合同测试。相同根因假设没有新的静态证据或实现变化时，不得消耗下一次页面执行机会。
- 调试开始 10 分钟内必须写出当前根因假设、反证和下一条最小验证；无法形成时转入诊断检查点，不得继续无边界探索。

## 全量回归与整改放量分流

- `full-regression` 用于回答当前版本全部执行候选的真实结果；它必须独立于整改优化计划，不能以业务 canary 通过作为全量执行前置条件。
- `incremental`/`repair` 用于控制整改或批量放量风险，必须经过静态合同、canary 收据和 `ready-for-batch` 门禁；该门禁不得阻断用户明确授权的业务全量回归。
- 两种执行模式必须互斥：全量回归不得携带优化计划或阶段参数；增量整改不得伪装成全量回归。混用须在认证、造数和浏览器启动前阻断。
- 全量执行过程中单条失败不得阻断后续独立批次；执行完成后按产品失败、自动化缺口、证据缺口、环境失败和瞬时平台失败统一分析。`selected=executed` 时即使存在失败或证据缺口，也必须记录为 `completed-with-findings`，不能伪装为 `blocked`。
- 全量执行的完成事实、用例失败事实和通过资格是三个不同事实：完成执行不等于通过，自动化缺口不等于产品缺陷，旧结果不因流程修复自动变成当前结果。

## 流程与项目物理隔离门禁

- 公共流程实现必须位于独立平台目录；业务项目只能保留兼容桥、应用适配器、领域资产、运行证据和应用级治理清单。
- 公共平台只能保存通用源码、通用脚本、通用契约测试和无项目身份的模板；具体应用的 readiness、执行账本、评审队列、发布裁决、迁移报告和接入文档必须写入该应用项目目录。
- 公共平台不得提供指向自身目录的项目产物默认路径。项目适配器必须显式提供产物根目录，且路径解析必须拒绝 `..` 等目录越界。
- 每个接入应用必须提供迁移闭环清单，覆盖公共平台与应用工作区的全部在管文件，并将其唯一归类为：`public-core`、`project-adapter`、`domain-asset`、`generated-evidence`、`history` 或 `transient`。
- 未归属文件、商品项目中的重复公共实现、非适配桥、当前合同断裂引用、文档与机器引用冲突、错位瞬态文件或公共目录项目内容任一非零时，迁移或流程优化只能声明“未完成”。
- TypeScript 依赖检查必须使用语法树识别真实导入，不得把代码生成模板、测试夹具或文档中的示例 import 误判为当前依赖。
- 当前执行合同和冻结历史快照必须分开裁决：当前来源断裂阻断交付；历史快照旧路径必须保留诊断和迁移决策，但不得冒充当前合同失败。
- 仍被机器合同引用的历史目录必须明确标记“暂不可删除”；文件名包含“待废弃”不能作为删除依据。
- 迁移闭环输出、第三方依赖、密钥和登录态只能通过明确排除策略处理，不得用宽泛忽略规则掩盖业务资产；`deliverables/**` 不能因为是生成文件就自动获得公共平台归属。
- 连续两次无输入变化的迁移审计必须产生相同输入指纹；Allure、Playwright 瞬态内容和审计报告自身不得造成结果漂移。
- 应用迁移闭环通过只证明该应用目录和公共流程边界正确，不得替代跨方案、跨应用的平台最终完成门禁。

## 稳定五维状态模型与状态裁决

测试资产必须区分正式绑定、脚本生成、历史运行、修复队列和当前标准执行收据。最终状态只能由公共状态裁决器根据 `caseFingerprint + implementationFingerprint + formalDisposition + standardReceipt` 计算，不能读取摘要文件中的最终字符串。

代码或页面适配器变化后，旧收据只能作为历史事实；未产生修复后的标准收据时，用例进入待重验，不能继续显示为当前通过，也不能把旧失败继续显示为当前产品缺陷。只有带完整页面、API、清理证据并绑定当前两类指纹的失败，才能进入产品偏差。

跨日期或切换对话框不会使完整收据失效；实现指纹或发布身份变化才会触发影响范围重验。旧格式收据在迁移期保留可追溯性，但不得静默升级为当前实现证据。

该模型是所有 SaaS、Tomcat + WAR、容器、多节点及无版本接口系统的公共不变量：

1. `executionStatus`：本次实际运行结果，只由断言与清理证据决定。
2. `evidenceStatus`：执行收据是否完整；截图、视频和脚本自报不能代替完整收据。
3. `applicabilityStatus`：结果适用的环境、租户、角色、语言、路由和业务上下文。
4. `changeObservation`：已观测的发布、配置、功能开关或合同变化；允许为 `unavailable`。
5. `reuseStatus`：`reusable`、`run-only` 或 `invalidated`，由证据完整性和明确变化共同决定。

固定裁决规则：

- `executionStatus=passed` 且 `evidenceStatus=complete` 时，本次执行成立，不要求存在发布身份。
- 发布身份可信且稳定时可自动复用；发布身份不可用时记录为 `run-only`，历史通过仍永久有效。
- 日期变化、切换对话框、重启工具或重新打开 Allure 报告不得改变任何历史执行状态。
- 只有明确的影响性变化、用例指纹变化、执行上下文不兼容、证据不完整或新的验收范围才触发增量验证。
- 旧 Allure、旧运行账本或模块运行报告缺少新版标准收据时，先进入证据协调，不得直接按全量重跑处理。
- 发布身份采集按系统适配器实现，不能把请求 ID、链路 ID、CloudFront 节点、响应时间或业务响应长度当作发布身份。
- 架构决策详见 `Merchant Center UITest/docs/adr/ADR-001-execution-result-and-release-observation.md`。
