# 流程反向场景跨项目执行方案

日期：2026-09-04  
范围：`public-core` 场景目录与覆盖评估；各项目只提供适配器映射。  
执行边界：不启动业务页面、不写入商品中心、不启动跨 `applicationId` 试点。

## 1. 目的

将反向生成从商品中心专用动作提升为跨项目流程能力，使每个流程场景都能由稳定场景 ID 触发，并追溯到来源、证据、用例、Recipe、绑定和人工异常原因。

## 2. 设计

1. 公共层维护 `ReverseScenarioCatalog`：场景 ID、FR/C 来源、触发事件、所需证据、允许动作、强制合同和人工升级条件。
2. 项目适配器只提交 `scenarioId -> caseId` 映射、项目来源和领域证据，不复制公共状态机或回写逻辑。
3. 触发事件先经过现有 runtime-audit V2 新鲜度、上下文、指纹、覆盖和写入安全门禁，再生成 `no-change/correct/add/delete/split/merge/block/revalidate` 候选。
4. 公共覆盖评估器输出 `covered/partial/missing`，缺失或部分覆盖不能伪装成流程完成。
5. 业务规则变化、拆分/合并、危险写入、来源冲突和证据不足统一进入人工异常队列；正常技术绑定和证据校正可按现有 AI 策略自动处理。

## 3. 执行步骤

### W1 公共合同

- 发布场景目录类型、校验器和覆盖评估器。
- 增加系统无关正向/负向合同：重复 ID、缺少来源/触发证据/合同、缺少映射、部分证据、跨项目重复映射。

### W2 流程项目接入

- 以 `process-reverse-scenario-catalog-v1.json` 登记 FR-001～FR-026。
- 每个项目在适配器中提供场景映射；没有流程用例的场景先标 `missing`，不得自动创建空壳 Recipe。
- 将现有商品中心反向结果标记为 `domain-asset`，不当作流程项目覆盖。

### W3 反向生成执行

- 仅消费当前、已登记、已消费且上下文匹配的证据。
- 先生成 provisional 候选，再由公共协调器校验来源、语义、覆盖、绑定、清理和权限。
- 通过 `autoApprovalPolicy` 的技术校正自动回写；业务规则和结构变化按策略转人工。

### W4 结果消费

- 同步更新正式用例、Recipe、绑定、覆盖矩阵、运行账本和项目索引。
- 为每个变更写入 correction ID、前后指纹、影响 caseId、证据哈希和审计事件。
- 仅受影响 caseId 进入增量重验；文档/报告变化不触发业务重跑。

### W5 验收

- 公共类型检查与场景合同测试通过。
- 每个接入项目输出场景覆盖报告，逐项显示 `covered/partial/missing`。
- `missing/partial`、跨应用试点缺失、迁移未完成和 30 天指标不足继续保持 `deferred/not-ready`，不改写业务通过结果。

## 4. 方案合理性复核

- **范围完整**：26 个 FR 场景均有稳定 ID，9 个公共合同作为强制依赖。
- **职责正确**：公共层负责目录、门禁和评估；项目层只负责业务来源与适配映射。
- **安全可控**：反向结果先是候选，证据/上下文/指纹/清理不完整即阻断或转人工。
- **可恢复**：结果按 caseId 和指纹增量消费，避免无意义全量重跑。
- **可审计**：来源、证据、决策、前后指纹和人工升级原因均可追溯。

## 5. 复核后补充的防遗漏项

1. 场景目录自身必须版本化并参与治理指纹。
2. 一个场景允许跨项目多用例映射，但同一项目重复 caseId 必须去重并告警。
3. 场景缺失映射时只输出 `missing`，禁止自动生成空用例。
4. 证据完整但当前用例过期时输出 `partial`，必须走重验，不得直接回写。
5. 外部 Git/CI/Webhook 只产生候选触发，未授权不得执行。
6. 反向生成结果不得直接晋级 formal 业务规则，仍遵守人工批准门禁。

## 6. 影响

本次优化属于 `public-core + domain-asset + generated-evidence`。不重跑、不失效 Merchant Center 已通过业务用例；新增公共实现会使未来正式业务执行重新计算实现指纹，仅对实际受影响用例定向重验。

## 7. 本次执行结果

- 流程项目已建立 26 条 `PROC-FR-001~026` 合同型候选用例，全部绑定来源和公共合同，执行资格保持 `false`。
- 商品中心已登记 10 个基于现有 runtime-audit 证据的跨项目映射，全部标记 `partial`；未将局部组模块证据升级为全项目覆盖。
- 流程覆盖从“26 missing”变为“26 partial、0 missing”；只有补齐真实项目适配器证据并通过公共收据门禁后，才能转为 `covered`。
- 本次未启动商品中心页面、CRUD 或跨 `applicationId` 试点，既有通过结果保持不变。

## 8. 双项目优化分析与执行优先级

| 项目 | 已有能力 | 需要优化 | 优先级与动作 |
|---|---|---|---|
| 流程项目 | 26 条场景目录和合同候选用例已建立 | 缺少真实项目适配器证据、运行收据、流程查询/导出入口 | P0：补齐来源/证据/映射；P1：接入实时事件、状态查询和人工队列；P2：趋势、flaky、聚类和 CI 回写 |
| 商品中心 | 5 个组模块 runtime-audit 用例已有证据，10 个场景映射候选 | 仅局部模块；执行 grant、全方案 API 生命周期、全量清理和跨系统试点未闭环 | P0：把映射接入现有 runtime-audit V2 并按 caseId 对账；P1：扩展到商品/输入/调味模块；P1：补真实目标系统前保持 deferred |

## 9. 复核后的执行顺序

1. 先完成流程项目 26 条候选用例的来源、公共合同和项目适配器映射校验。
2. 再消费商品中心已有 5 个 runtime-audit case 的证据，生成跨项目 `partial` 覆盖，不触发业务重跑。
3. 对 `partial` 场景逐项补齐缺失的 execution grant、完整事件流、API/UI 清理或全方案范围证据。
4. 只有当前指纹、上下文和完整收据同时满足时，才把场景从 `partial` 转为 `covered` 并进入增量重验计划。
5. 任何来源冲突、规则变化、危险写入、跨应用缺失或迁移漂移，保持人工/平台异常，不自动放量。

复核结论：方案没有把局部商品中心证据误当公共完成，也没有引入未经来源支持的业务字段；范围、权限、证据、清理、状态和跨系统边界均有明确停止条件，可以按本方案继续执行。
