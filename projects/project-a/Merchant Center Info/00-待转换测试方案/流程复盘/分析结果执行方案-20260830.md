# 测试方案、页面审计与老旧用例治理执行方案

生成时间：2026-08-30（Asia/Shanghai）  
执行边界：Merchant Center 静态审计、合同校验、计划生成和检查点记录；允许执行自控参考系统的公共平台回归验证。未经金将军明确启动，不执行跨 applicationId 正式试点、Merchant Center 正式业务写操作或 Merchant Center 历史用例全量回归。

## 1. 目标与范围

本方案处理三项问题：

1. 使用页面/API 审计补充正式测试用例的可执行步骤，但不从观察结果猜测业务规则。
2. 通过输入指纹、页面 Probe、事件触发和新鲜度合同保证审计页面信息可消费。
3. 在生成前和执行前识别老旧测试方案，保留历史并仅对受影响 `caseId` 进行重审和定向重验。

变更范围分为：

| 范围 | 本次处理 | 结果影响 |
| --- | --- | --- |
| `domain-asset` | 形成执行方案、遗漏登记、验收口径 | 既有通过结果不变 |
| `public-core` | 修复并验证参考系统上下文、证据收据和参考验证模式 | 仅影响公共参考验证，不触发 Merchant Center 业务重跑 |
| `project-adapter` | 仅校验 Merchant Center 输入、页面合同、来源和清理映射 | 不改变用例状态 |
| `generated-evidence` | 生成本方案和静态执行检查点 | 作为治理证据，不授权业务通过 |

## 2. 已有能力与缺口

### 已有能力

- 测试方案输入校验来源、语义、覆盖和可执行性。
- 正式用例、绑定、执行状态、产品偏差和延期状态分离。
- 计划、绑定、来源和运行审计指纹支持增量选择。
- 页面/API Probe、页面 Diff、标准收据、清理收据和脱敏合同已存在部分实现。
- 公共平台禁止用历史报告、截图、聚合计数替代当前标准收据。

### 本轮补充的遗漏

| 遗漏项 | 补充控制点 | 处理时机 |
| --- | --- | --- |
| 来源之间可能冲突 | 建立来源优先级、冲突队列和人工确认关闭条件 | 用例生成前 |
| 审计报告存在但可能不是最新 | 增加 `observedAt`、上下文、页面/网络指纹、`freshUntil`，过期或未知按不可消费处理 | Probe 和生成前 |
| 审计触发可能重复或丢失 | 事件去重、按页面/用例影响范围编排、失败 checkpoint 和恢复 | 触发与恢复时 |
| 老旧用例可能被错误当成产品失败 | `stale-suspected`、`stale-confirmed`、`superseded` 与 `product-defect` 分离 | 生成前和执行前 |
| 写入用例可能残留测试数据 | 服务端 ID、唯一业务身份、API/UI 双重清理和 finally 清理 | 绑定和执行前 |
| 审计产物可能覆盖最新结果 | 临时文件写入、完整性校验、latest 指针原子更新、历史不可覆盖 | 报告生成时 |
| 计划可能漏掉排除项或分母 | `planned = eligible + exclusions` 守恒，逐条记录排除原因 | 计划生成时 |
| 重试可能重复写操作 | 非幂等操作先查询身份，不能盲目重试；保存 checkpoint 后再恢复 | 运行时 |
| 证据可能泄露敏感信息 | 报告、日志、checkpoint 写入前递归脱敏，禁止密码、Token、Cookie 和授权头 | 全流程 |
| 规则或页面变化可能没有责任闭环 | 变更来源、影响 `caseId`、负责人、关闭条件和 SLA | 差异审计后 |
| 自控参考验证可能被历史修复账本误阻断 | 参考验证显式使用已授权 `full-regression`，不绕过生产修复门禁 | 参考验证时 |

## 3. 执行步骤

### 阶段 A：资产与来源准入

1. 读取 `FINAL-GOAL.md`、测试方案入口、用例库、已完成/未落地索引和待处理入口。
2. 校验每个正式用例唯一 `caseId`、来源 ID、前置条件、步骤、预期、Claim、验证通道和清理适配器。
3. 计算业务语义指纹和来源指纹，识别新增、修改、删除、替代、冲突和来源阻断。
4. 来源冲突进入 `review-required`，不得由页面审计结果自动覆盖业务规则。

### 阶段 B：审计新鲜度与页面补充

1. 对每个模块执行只读页面/API Probe。
2. 采集路由、控件、字段、按钮、弹窗、接口、关键响应和页面上下文。
3. 为审计产物记录 `observedAt`、应用版本、环境、租户、角色、语言、页面指纹、网络指纹、来源指纹和 `freshUntil`。
4. 生成结构化 Diff：`clean-diff`、`technical-drift`、`source-drift`、`unknown`。
5. 仅把 `clean-diff` 且上下文匹配的审计结果提供给用例生成；`unknown` 或过期结果进入复审。

### 阶段 C：用例生成与补充

1. 先生成业务语义骨架，再由审计补充可观察操作细节。
2. 每个预期拆为独立 Claim，并绑定来源、验证信号、断言适配器和证据等级。
3. 写入用例必须绑定造数、服务端身份、API/UI 验证和对象级清理。
4. 运行反向得到的步骤只能进入 `provisional` 配方候选，不能直接覆盖正式业务语义。
5. 通过来源、语义、覆盖、可执行性和生成质量门禁后，才生成正式绑定。

### 阶段 D：执行前影响分析

1. 对比当前用例、来源、绑定、页面审计、实现和执行上下文指纹。
2. 指纹不一致的用例标记 `revalidation-required`，不得复用旧通过收据。
3. 按 `caseId` 计算增量选择集；不受影响的用例保持既有结果。
4. 校验 `planned = executionEligible + classifiedExclusions`，分类包括延期、来源阻断、技术阻断、产品偏差和不适用。
5. 在认证、造数和浏览器启动前校验执行授权、选择集、路由、上下文和 checkpoint。

### 阶段 E：允许的本轮执行

本轮只执行以下内容：

- 静态来源、用例、绑定、覆盖和资产索引校验。
- 公共平台合同测试和项目适配器合同测试。
- 页面合同与生成输入的只读一致性检查。
- 计划和检查点生成。
- 自控参考系统公共平台回归验证；该验证不代表跨 `applicationId` 正式试点。

本轮不执行以下内容：

- 跨 `applicationId` 的系统试点。
- Merchant Center 正式业务写入、创建、修改、删除。
- 因文档或报告变更而重跑已通过用例。
- 将审计不完整、定位失败、超时或认证失败登记为产品缺陷。

### 阶段 F：结果消费与恢复

1. 静态或合同执行失败只登记为治理/自动化缺口，不改变业务结果。
2. 业务执行必须由公共平台标准收据裁决，不能由本方案或索引自行判定通过。
3. 中断时保留 checkpoint，恢复时只复用相同计划指纹、选择集指纹和完整收据。
4. 非幂等操作发生连接异常时先按服务端 ID 或唯一业务身份查询，再决定是否继续。
5. 任何新建对象都立即登记 server ID，并在 finally 中执行清理和残留核验。

## 4. 验收标准

- 所有正式用例可反向定位到来源、页面/API 审计或人工确认；来源冲突不会静默通过。
- 页面审计报告具备上下文、来源、页面/网络指纹和新鲜度状态。
- 过期、未知上下文或结构化 Diff 不完整的审计结果不能进入正式生成和正式通过裁决。
- 老旧用例保留历史，准确分为复审、替代、延期、不适用、来源阻断或产品偏差。
- 执行计划逐条对账 `caseId`、用例、绑定、计划、运行账本和索引。
- 计划分母守恒，排除项不被误计为失败或通过。
- 任何正式通过均需要当前标准收据、逐 Claim 断言收据和要求的清理收据。
- 所有报告、日志和 checkpoint 均通过敏感信息扫描。
- 本轮静态执行和自控参考验证不修改既有 Merchant Center 业务结果；跨 `applicationId` 正式试点保持 `deferred`。

## 5. 结果状态约定

本方案属于 `domain-asset + generated-evidence`。方案生成、遗漏检查和静态合同执行完成后，历史业务结果标记为“未重跑、未失效、保持不变”。未来实施公共能力时，必须同时提供公共合同、Merchant Center 适配器合同和系统无关负向测试；仅修改项目脚本不视为平台能力完成。
