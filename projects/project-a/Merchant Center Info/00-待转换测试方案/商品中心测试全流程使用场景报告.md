# 商品中心测试全流程使用场景报告

> 版本：2026-09-01  
> 范围：测试方案输入、用例生成/变更、业务规则确认、技术绑定、执行、证据、状态裁决、修复、索引与平台评审。  
> 依据：`FINAL-GOAL.md`、统一入口 `README.md`、公共平台 `Test Automation Platform/AGENTS.md`、商品中心流程文档及当前索引/阻断登记。

**变更范围**：`generated-evidence`（流程分析报告）；不修改 `public-core`、`project-adapter` 或 `domain-asset`，不重跑业务用例，既有运行结果与索引保持不变。

## 1. 报告目的与边界

本报告把“测试资产发生变化后，系统应该如何反应”整理为可执行场景。每个场景均说明：

- 触发条件与适用范围；
- 必需输入及证据来源；
- 自动处理、人工处理和禁止行为；
- 产物、状态和通过资格；
- 异常分类、恢复方式及对既有结果的影响。

报告只描述流程和使用场景，不修改正式用例、不启动业务执行。商品中心模块交付和跨应用平台通用化是两个独立结论。

## 3. 端到端主流程

```text
来源/测试方案接收
  → 来源登记与指纹
  → TestCase IR 规范化
  → 语义、覆盖与证据审计
  → 技术绑定与 Recipe 编译
  → 合同/安全/就绪门禁
  → 执行意图与增量选择
  → 认证、上下文守卫、造数
  → UI/API/下游业务操作
  → 逐 Claim 断言与清理
  → 标准执行收据
  → 状态裁决与索引刷新
  → 失败分类/人工确认/定向修复
  → 复验、发布与平台评审
```

每条用例必须以 `caseId` 为主键，并能对账 `ruleId`、`recipeId`、`dataProfileId`、用例指纹、实现指纹、执行上下文和收据。标题或批次名称不能代替这些身份。

## 4. 场景目录（逐环节）

### 场景 A：输入一份新的测试方案，生成正式用例

**触发**：收到 PRD、XMind、Markdown、Word 或现有用例，放入统一入口的 `待处理/`，或通过 intake 命令指定输入文件。

**输入要求**：每条用例有唯一 canonical `caseId`、模块、优先级、精确来源、前置条件、步骤、可观察预期；写数据用例还要声明造数与清理。输入不应包含 selector、固定等待、账号、Token、Cookie 或浏览器存储状态。

**处理流程**：

1. 读取来源并登记 `sourceRegistry`、路径/定位、文件指纹和证据等级。
2. 转换为 TestCase IR：补齐语句级 Claim、覆盖分母、角色/环境/能力、数据档案、终态和清理合同。
3. 运行结构校验、来源绑定、语句唯一证据校验、路由/控件/弹窗/校验覆盖审计。
4. 读取运行时审计校正合同；符合 `autoApprovalPolicy` 的确定性校正可自动进入候选，否则进入 `review-required`。
5. 只有来源、语义、覆盖、断言面、操作键、上下文和清理均完整，才允许编译 Recipe。

**推荐命令**：

```powershell
npm run build:product-center:test-plan-intake-v1
npm run audit:product-center:test-case-input -- --input <用例IR.json> --bindings <来源绑定.json> --scope full
```

**产物**：规范化 IR、来源绑定、覆盖分母、审计报告、Recipe/候选规则、编译检查点。正式正文仍只保留在 `用例库/<模块>/正式测试用例.md`。

**状态与门禁**：`passed`/`ready` 只表示通过相应生成或执行门禁；`review-required`、`invalid`、来源阻断或覆盖缺口不得生成可执行 Recipe。不能凭标题、行业惯例或旧脚本猜字段、接口、提示或业务规则。

**既有结果影响**：新增用例不影响其他用例；若新用例复用了既有语义，必须合并，或提供变体 ID 和独立来源，避免重复计数。

### 场景 B：已有测试方案被修改

**触发**：正式 Markdown、PRD/XMind 来源、Claim、步骤、预期、优先级、覆盖项或来源指纹发生变化。

**自动识别**：计算候选指纹/用例指纹，比较来源、规则、绑定、执行计划、运行账本和证据文件。日期、查看报告、切换对话框、重新启动工具等非语义变化不得触发重跑。

**分流**：

- 仅排版或不参与指纹的说明元数据：结果保持不变；
- 前置、步骤、预期、精确提示、字段、弹窗或断言面变化：受影响用例转 `ready/revalidation-required`；
- 用例新增、删除、拆分、合并：更新正式正文、绑定、计划和索引，禁止只改汇总文件；
- 来源冲突、删除/合并未获策略授权、证据不完整：转人工异常队列，不自动降低断言精度。

**后续动作**：运行闭环审计 → 证据协调 → 生成增量选择 → 明确批准 `caseId` → 定向执行。旧结果保留为历史事实，但不得继续作为当前通过依据。

### 场景 C：人工修改业务规则（例如改“商品分类是否必填”）

**触发**：产品/业务负责人明确确认规则，或确认页面实际行为与原规则不一致。

**记录内容**：规则 ID、旧/新语义、适用应用/业务域/环境/角色/语言/路由/开关、来源文件和指纹、确认人/时间/理由、受影响 `caseId`、冲突与 supersedes 关系。

**处理流程**：

1. 将人工确认写入规则评审/事件账本，生成候选规则和变更事件；
2. 比较规则指纹和受影响断言面，生成 `rerunCaseIds`；
3. 更新正式用例、技术绑定、Recipe、执行计划（不能只改文案）；
4. 运行证据仍只能把候选规则推进到 `ready-for-human-review`，不能自动升级为 formal；
5. 人工批准匹配候选指纹后，受影响用例进入统一增量执行。

**必须重跑的变化**：前置、步骤、预期、精确提示、控件/字段身份、弹窗顺序、UI/API 断言面、handler/locator、数据工厂、API 映射、清理策略、发布/配置/开关或执行上下文变化。

**不触发重跑的变化**：日期、报告说明、对话框查看时间、仅文档排版且不参与用例指纹的元数据。

**结果处理**：新标准收据产生前，旧通过只能标为历史或待重验；产品缺陷只有在当前 UI/API 稳定终态证明预期错误时才能关闭为修复后通过。截图可支持人工确认，但不能替代运行。

### 场景 D：页面/API 发生技术漂移

**触发**：路由、侧边栏能力、可见控件、必填字段、弹窗、按钮状态、API 方法/路径/响应形状变化。

**流程**：`probe → diff → proposal → approval → apply technical repair → impacted → full/targeted → baseline`。页面网络采集必须脱敏，保留方法、路径、字段形状、状态和上下文；新 API 先形成观测提案，不能凭一次请求覆盖正式 API 合同。

**门禁**：技术修复要记录 proposal 指纹、变更文件、before/after SHA-256 并验证当前文件命中 after 哈希；来源、Claim 或运行验收阻断不能被技术审批绕过。

**影响**：绑定/实现指纹变化使旧业务收据不可复用，但不自动判产品失败；只执行受影响用例，避免无依据全量重跑。

### 场景 E：生成技术绑定与 Recipe

**触发**：用例通过 intake 审计，准备进入自动化。

**绑定内容**：路由、`navigation.sidebar.open`、页面/控件能力、数据 profile、操作键、断言 adapter、观察通道与权威、API 映射、清理 adapter、Claim ID。

**只读用例**：禁止声明 seed、mutation、cleanup。  
**写入用例**：必须同时声明 seed、真实 operation、UI/API 断言、API/UI 零残留清理；即使业务预期“不落库”，只要声明 API mutation 或 cleanup，也进入写通道。

**失败场景**：缺精确绑定、未知覆盖 ID、缺清理、Claim 未逐项覆盖、语义重复、上下文不完整、实现漂移或敏感信息出现时，停在编译/审计阶段，不启动浏览器。

### 场景 F：执行前选择（增量、修复、全量）

**增量/repair**：由明确影响集和公共 revalidation decision 驱动；当前用例指纹、实现指纹、上下文和完整收据匹配时可 `reuse`，其余受影响用例定向执行；`unknown-impact` 只能在数量/比例上限内作为 sentinel。

**full-regression**：回答当前版本全部执行候选的真实结果；不携带优化计划或阶段参数，不消费 canary 作为前置条件。单条失败不得停止独立批次。

**硬阻断**：模式参数混用、筛选参数非法、计划选择集与 runner 实际选择集出现 missing/unexpected、旧意图复用、缺分区/路由、授权过期或已撤销，在认证、造数和浏览器启动前失败。

**产物**：execution intent、选择集/范围指纹、计划、检查点。检查点必须保存意图指纹、选择集指纹、已达终态和未完成用例。

### 场景 G：认证、业务上下文和在线预检

**触发**：执行授权签发且计划通过静态门禁。

**顺序**：统一 runner 校验 `applicationId + runId + 精确 caseId 集合` 的短期授权 → 认证 → 只读在线 Probe → 路由/语言/角色/租户/服务端 ID 或唯一业务身份守卫 → 进入业务动作。

**失败归类**：登录页未识别、商户选择失败、主界面不可达、认证失效、网络超时、连接重置、定位漂移、下游能力缺失属于环境/技术/外部依赖；不能直接写成产品失败。

**安全要求**：日志、检查点和报告不得保存密码、Token、Cookie、Authorization 或浏览器存储状态，只能保存脱敏元数据。

### 场景 H：数据造数与业务写操作

**触发**：用例声明可变更数据且 mutation-ready。

**造数**：使用可清理的 `dataProfile`，不得依赖环境中共享既有数据。每次创建立即登记 server ID、唯一身份、变体、依赖关系和 cleanup ledger。

**写操作**：每个 `operationKey` 必须有且仅有一个真实操作收据，或明确的终态失败/中断收据。非幂等写入不自动重试；发生超时/重连时先按 server ID 或唯一身份查询是否已生效，再决定恢复或清理。

**按钮置灰**：只能证明未提交，不得伪造写请求收据；提交前禁用态不能写成“已提交”。

### 场景 I：业务断言与证据收集

**触发**：操作完成或出现终态反馈。

**断言要求**：每个预期 Claim 生成独立 expect/断言收据，记录 expected、actual、观察通道（UI/API/downstream/cleanup）、验证权威、比较结果和最终状态；业务动作前和断言前均要有 context guard 收据。

**观测优先级**：用户可见行为以 UI 为主；API 用于持久化、结构完整性、异步同步辅助。用例同时声明 UI 与 API 时必须分别形成收据，API 不能替代 UI。

**超时分类**：探针无响应为 `WAIT_UNTIL_PROBE_TIMEOUT`；已响应但条件未满足为 `WAIT_UNTIL_CONDITION_TIMEOUT`。超时、字段不可观测、定位失败不能推出“保存失败/未同步”。

### 场景 J：清理与零残留验证

**触发**：写入用例完成、失败、熔断或中断恢复。

**流程**：执行系统恢复 adapter → 按 cleanup ledger 删除/恢复对象 → API 查询零残留 → UI 查询零残留 → 写入清理收据。`ui-verification-unavailable` 不等于零残留。

**失败影响**：任一 API/UI 清理证据缺失，即使 Playwright 通过也不能进入 `passed`；保留 server ID 和残留诊断，下一次 setup 先恢复历史未完成检查点。

### 场景 K：标准收据导入与状态裁决

**触发**：runner 完成或产生终态失败/中断收据。

**收据最小匹配键**：`caseId + caseFingerprint + implementationFingerprint + executionContext + executionBatch`，并覆盖所有 Claim、operation、context guard、断言和清理证据。

**五维/独立状态**：

| 维度 | 含义 |
|---|---|
| `executionStatus` | 本次真实运行的断言/清理结果 |
| `evidenceStatus` | 收据是否完整 |
| `applicabilityStatus` | 环境、租户、角色、语言、路由和业务上下文是否适用 |
| `changeObservation` | 发布、配置、开关或合同变化观测，可为 unavailable |
| `reuseStatus` | `reusable`、`run-only` 或 `invalidated` |

只有当前收据完整且断言/清理成立，才具备本次 `passed` 资格。发布身份不可用不否定本次通过，但通常只能是 `run-only`，不能自动声明跨发布复用。

### 场景 L：失败分类与责任路由

| 分类 | 判定依据 | 后续路由 |
|---|---|---|
| `product-failure/product-defect` | 当前 UI/API 稳定终态明确证明预期不成立，且上下文、操作、断言、清理完整 | 产品偏差目录，修复/规则确认后定向重跑 |
| `automation-gap` | selector、handler、Recipe、断言映射、数据工厂或清理实现缺陷 | 修自动化，补合同测试，不改产品结论 |
| `environment-failure` | 认证、网络、浏览器、服务不可达、超时、连接重置 | 有界恢复，保留检查点 |
| `external-dependency` | 行业商品、C 端、POS、终端或下游能力不可用 | 明确延期，登记恢复条件 |
| `evidence-gap/revalidation-required` | 收据缺字段、旧格式、指纹/上下文不匹配或历史证据未协调 | 先证据协调，无法证明时进入重跑审批 |

产品偏差不得自动转通过；延期不得标失败/通过/删除；旧失败不能覆盖后来已接受的整改结果。

### 场景 M：历史证据协调

**触发**：历史 Allure、运行账本或报告存在，但不满足新版标准收据。

**流程**：先建立旧收据适配任务，按 `caseId`、旧指纹、证据文件哈希和上下文尝试补录；补录成功则保留历史并按规则判断是否可复用；补录失败且无法证明完整执行，才进入显式重跑审批。不能因为报告文件存在或汇总通过数高就直接授权 `passed`。

### 场景 N：定向修复与重试

**触发**：确定性自动化失败、产品偏差修复、规则确认后需要重验。

**预算**：每修复轮最多 2 次、最长 15 分钟；同一用例/指纹最多 2 轮。确定性失败在实现指纹未变化前不得再次启动浏览器；瞬时平台失败按约定最多有界重试一次。达到上限必须先写结构化诊断（根因、修正、证据引用），再决定下一轮或技术复核。

**最小验证**：先做类型检查、受影响合同测试和局部脚本，再执行页面；失败后只跑受影响脚本。完整通过后才统一刷新执行计划、账本和索引。

### 场景 O：批准增量执行

**触发**：闭环审计和证据协调完成，产生当前 `recommendedCaseIds`。

**流程**：人工明确批准精确 `caseId`（拒绝延期、不可用和已解决用例）→ 打印执行计划 → 使用 `--execute` 启动页面。名单过期或为空时停止，绝不能静默退化为全量运行。

**标准链路**：

```powershell
npm run audit:test-plan:closure
npm run flow:test-plan:evidence-closure
npm run approve:test-plan:incremental -- --case-ids=<id1,id2> --approved-by=<operator>
npm run test:test-plan:approved-incremental
npm run test:test-plan:approved-incremental -- --execute
```

### 场景 P：全量回归

**触发**：用户明确要求当前版本全部执行候选的真实结果，或发布验收需要全量结果。

**规则**：独立于整改计划，不携带 canary/batch 优化参数；选择集固定后逐批执行，单条失败继续其他独立批次。结束后统一分类，整体状态可为 `completed-with-findings`；只有执行未完成或启动前被阻断才是 `blocked`。

**影响**：全量回归会刷新当前版本结果，但不会把自动化缺口、环境故障或旧历史自动改成产品失败；已通过用例不因流程优化而自动重跑，除非指纹/语义/上下文或用户明确要求发生变化。

### 场景 Q：中断、断点恢复和瞬时平台失败

**触发**：连接重置、超时、429、进程消失、外层超时或机器重启。

**处理**：保存检查点后对只读/幂等动作按约定退避重试；非幂等动作先查询 server ID/唯一身份确认是否已生效，禁止盲目重放。恢复时只复用当前指纹、当前选择集且已有完整收据的批次，从首个未完成单元继续。

**结论**：平台故障与产品结果分开记录；不能因为 Codex 连接或上游模型限流就把用例判失败。连续达到预算时安全停止受影响单元，保留证据并继续独立工作。

### 场景 R：资产索引、运行账本和报告刷新

**触发**：正式用例、绑定、运行结果、分类或处置状态发生有效变化。

**必须同步**：canonical 正文、automation binding、execution plan、runtime ledger、`已完成/index.*`、`未落地/index.*`、产品偏差/延期索引和报告。索引由生成命令构建，不能人工编辑“已完成/未落地”汇总。

**状态隔离**：`handlingStatus`、`verificationStatus`、`actionRequired` 独立保存；“已整改待旧收据迁移”不能重新进入执行候选；已完成目录不代表运行通过。

### 场景 S：跨方案、跨业务域、跨应用平台评审

**触发**：希望宣布公共流程通用完成，或准备平台正式发布。

**门禁**：公共实现、项目适配器、系统无关负向合同、参考基线、不同业务域以及至少一个不同 `applicationId` 的真实目标系统（登录、可逆 CRUD、完整 UI/API/清理收据）均通过，并由人工平台评审批准。自建参考系统只能验证框架机制，不能替代真实目标系统。

**当前限制**：跨应用试点只能由用户明确启动；当前登记为 deferred，恢复条件包括提供不同 `applicationId` 的目标系统、完成适配器、取得可逆真实试点完整收据。平台未完成不阻断已满足自身门禁的商品中心模块交付。

### 场景 T：运行时审计 V2 证据目录消费

**触发**：任何新方案生成用例、技术绑定或 Recipe 前，或已有方案准备重新编译。

**流程**：将截图、视频、DOM、网络和 API 查询放入方案专属证据根目录 → 对每个文件登记 SHA-256、采集时间、应用版本、环境、角色、语言及处置状态 → 建立 route/control/field/dialog/validation/api-operation/state 覆盖分母 → 生成 `no-change/correct-case/add-case/delete-case/split-case/merge-cases/block-case` 决策。

**门禁**：证据只能是 `consumed`、`not-applicable`、`stale`、`conflict` 或 `review-required`；未登记文件、越出项目根目录、哈希不一致、过期、上下文不一致、指纹漂移或正式来源冲突均阻断。每项 assertion 必须同时有机器可比对 `expectedValue` 和正式文本 `text`，任一不一致都不能生成。

**自动/人工边界**：命中 `autoApprovalPolicy` 的确定性校正可自动落地；策略未授权、危险写入证据不完整或 `block-case` 返回 `RUNTIME_AUDIT_AUTO_APPROVAL_DENIED`，进入人工异常队列。运行时自动校正不等于跨版本 formal 规则自动晋级。

### 场景 U：技术绑定候选审批、拒绝与失效

**触发**：页面合同或 Gold Recipe 已具备可复用能力，需要将 route、capability、assertion、Claim、seed、cleanup 编成正式绑定。

**流程**：生成候选及审批请求 → 人工逐条填写 `approved/rejected`、审核人、时间和理由 → 保持 candidate/page-observation fingerprint 与 candidate hash 不变 → 审批通过后编译 bindings、Recipes 和 generated spec → 再做独立 runtime acceptance 与零残留验收。

**拒绝/失效**：缺审批、任一拒绝、审批信息不全、候选或页面观测变化时编译失败；旧审批指纹不可复用，必须重新生成请求并重新审核。静态审批不能直接授权业务 `passed`。

### 场景 V：模块合同维护、策展与版本发布

**触发**：模块字段、路由、操作、排除项或来源合同新增/修改/墓碑删除。

**流程**：只修改对应模块源文件或导入证据 → 构建合同 → 验证合同 → 生成差异 → 精确影响分析 → 生成增量计划 → 合同测试/Recipe 测试 → 项目验收。跨模块人工结论统一进入 `human-review-decisions.json`，不直接编辑聚合 JSON。

**P0 审核批次**：按 OpenAPI 的 service/controller tag 分组，每包最多 20 条；人工只能给出 `confirm/exclude/defer` 等明确结论，批次生成器不把待确认项自动变成断言。

**正式发布**：人工提供版本、审核人和说明后执行 promote；命名、版本、追溯或合同错误则阻断。发布记录保存版本与审计链。候选/治理指纹变化会使旧 formal 发布自动降级为 `not-approved`，不能依赖人工发现。

### 场景 W：Gold 用例开发、onboarding 与维护

**触发**：新增或修改 Gold 用例，或需要把已通过 runtime acceptance 的配方纳入正式集合。

**阶段**：开发期只运行目标单例 → 单例通过且 runtime acceptance=accepted 后执行一次 onboarding → onboarding 内按 checkpoint 运行 single repeat=3、impacted、full → 全部完成后只执行一次本地维护。中断恢复首个未完成阶段，已完成阶段不重跑。

**禁止行为**：开发阶段不得直接运行 impacted/full/repeat=3；确定性 locator、strict-mode、uniqueness 失败必须先修实现，不能用瞬时重试掩盖。

### 场景 X：质量流水线分阶段执行

**触发**：提交变更、发布验收或用户要求执行商品中心质量流水线。

**顺序**：安全前置 → 构建 Recipe/Generation V1/Intake V1 → TypeScript、合同和 Recipe 合同测试 → `live/full` 模式执行轻量 Probe 与页面 Diff → `full` 模式执行主集合、Gold 和已审批技术绑定 UI → 以同一 `pipeline runId` 生成失败分析 → 分别计算 automationPlatformReady 与 testGenerationProductReady。

**分流**：`static` 只做静态门禁；`live` 增加在线 Probe；`full` 才执行完整业务集合。漂移固定走 `probe → diff → proposal → approval → technical-repair → impacted → full → baseline`，clean diff 是可接受 no-op；来源/Claim/运行验收阻断不得通过技术修复绕过。

### 场景 Y：Jenkins/CI 实时审计与构建归档

**触发**：在 Jenkins 或 CI 中运行系统测试并需要实时查看业务操作进度。

**流程**：设置 `SYSTEM_TEST_AUDIT_EVENT_LOG` → 每个 API/UI operation 完成后立即追加 `operation.called` JSONL 事件 → 运行结束后验证当前批次 `evidence-ledger.json` 的审计合同版本、操作/断言/清理覆盖和哈希链 → 归档事件 JSONL、JSON 报告、HTML 报告及门禁输出。

**异常**：门禁返回 2 时保留原始业务结果，但构建标记为“审计不完整/需补证据”，不得因此全量重跑；只有用例、实现、上下文或产品观察发生影响性变化才进入增量重验。事件写入采用文件锁、事件 ID 幂等和哈希链；日志必须递归脱敏。

### 场景 Z：迁移收口与项目文件治理

**触发**：公共平台能力迁移、项目适配器调整、产物根目录变化或需要关闭迁移任务。

**流程**：读取 `project-adapter.json`、artifact manifest 和迁移基线 → 预检文件归属（`public-core/project-adapter/domain-asset/generated-evidence/history/transient`）、路径越界、重复公共实现、断裂引用和哈希变化 → 有意变更时由批准人和原因接受新基线 → 调用公共生命周期刷新 readiness、评审队列、最终裁决、外部依赖和迁移报告。

**门禁**：无批准参数、无匹配收据、收据篡改、新增受管文件未接受或无变化重复接受时阻断；迁移收口不执行业务 UI，不因迁移完成重跑已通过用例。

### 场景 AA：报告-only、合同验证和业务执行隔离

**触发**：只想验证 reporter 格式、收据绑定、状态裁决、批次控制、迁移或平台合同，而非验证业务行为。

**处理**：使用 synthetic/isolated result directory 和合同测试，禁止为验证报告格式而重跑商品中心业务用例；公共门禁应消费结构化假数据和最小证据。

**结果**：只产生流程/合同验证结论，不改变业务运行账本、用例状态、历史通过或索引；报告-only 失败不得归类为产品失败。

### 场景 AB：能力索引、架构与生成资产维护

**触发**：新增、删除、移动或重命名 Page、Flow、Fixture、API、test-data、cleanup、evidence 或 audit 能力，或修改受治理 UI 代码。

**流程**：先读取 `docs/项目能力索引.md` → 修改后运行 `capabilities:generate`/`capabilities:check`、TypeScript、UI architecture lint 和受影响合同测试 → 生成文件只由生成器更新，不手工编辑。

**门禁**：Page/Flow 边界、稳定 locator、中文步骤、无固定等待、无敏感信息、无跨层非法依赖必须满足。结构门禁通过只证明实现可维护，不代表业务用例通过；架构债务基线不得为通过而上调。

### 场景 AC：接受/排除/延期及墓碑删除

**触发**：人工对来源冲突、能力缺失、重复语义、历史字段或无需自动化项作出明确处置。

**处理**：使用统一人工决策记录，区分 `confirm`、`exclude`、`defer`、`not-applicable`、`blocked-source` 和墓碑删除；每项必须有来源、理由、审核人，删除不得只凭文件名或生成文件中缺失判断。

**结果**：延期保留正式正文和恢复条件，不注册执行；不适用不计入执行候选但保留追溯；来源阻断必须进入未落地/阻断报告；任何处置变化都更新绑定、执行计划和索引，不能用负责人摘要清零分母。

### 场景 AD：跨项目验收与复用

**触发**：将商品中心已验证的流程推广到新项目或新系统。

**流程**：新项目只新增 `AcceptanceProject`/系统 adapter，声明认证、路由、实体、数据和清理；公共 acceptance 内核、检查点、扫描、脱敏和编排保持不变 → 执行项目扫描（默认复用同指纹 checkpoint，路由集合变化则重建）→ 取得目标项目证据。

**边界**：商品中心兼容投影只能证明 case/rule/dataProfile/门禁映射；同应用跨域只能证明跨方案复用；平台正式通用化仍必须有不同 `applicationId` 的真实目标系统证据和人工批准。

### 场景 AE：业务规则生命周期、时间上下文与历史迁移

**触发**：规则新增、修订、废止、适用范围变化，或需要把旧规则/旧收据迁移到当前合同。

**流程**：生成规则候选与生命周期快照 → 记录观察事件、来源指纹、revision、`effectiveFrom/effectiveTo`、环境/角色/语言/路由/开关上下文、冲突及 supersedes → 构建规则覆盖和场景覆盖 → 进行时间上下文审查 → 人工批准后推广 verified baseline。

**历史迁移**：旧规则只作为历史事实保留；迁移必须输出前后指纹、增删改清单、哈希链和批准人。旧规则不能因文件仍存在就继续作为当前断言，也不能因迁移脚本完成就自动把旧运行结果升级为当前通过。

### 场景 AF：原始 XMind/来源重建与冲突和解

**触发**：需要从原始 XMind、PRD 或历史 canonical 文件重建测试方案，或发现来源与运行事实不一致。

**流程**：原始来源只读保留 → 生成独立重建版 → 将每个 Claim、场景、变体和覆盖 ID 与来源定位绑定 → 运行 canonical conflict、重复语义、缺来源和历史字段审计 → 输出 `retain-canonical/update-canonical/needs-prd/product-defect/external-blocked` 等处置建议。

**边界**：运行观察只能形成技术证据和修订提案，不能静默覆盖业务意图；来源冲突必须由产品/业务确认或进入异常队列。重建版与原始版都保留指纹，避免历史追溯断裂。

### 场景 AG：API 生命周期、观测提案与批量生成

**触发**：页面捕获到新 API、已有接口方法/路径/响应形状变化，或需要生成品牌菜单 API 测试集。

**流程**：页面 Probe 捕获真实 request/response → 脱敏和路径归一化 → 与 `all.operations` 对比 → 已匹配接口只更新运行证据，新路径形成 observation proposal → 生成 API landing ledger、blocker plan 和测试候选 → 准备运行 → 执行并聚合结果。

**门禁**：服务归属、operationKey 冲突、请求/响应 schema 不完整、认证方式未知或只观测一次均进入人工异常；不得直接覆盖正式 API 文档。API 测试的通过仍需按操作收据、断言和清理合同裁决，不能以 HTTP 200 或汇总成功数代替。

### 场景 AH：受控整改关闭与交付收口

**触发**：修复轮次完成，或需要交付某一模块/商品方案但平台仍有跨系统阻断。

**流程**：核对修复账本、当前用例/实现指纹、标准收据、产品偏差/延期索引和清理结果 → 生成模块 closure、owner summary、blocked-source report 和最终状态 → 仅在逐用例收据完整时关闭受影响事项 → 保留平台 `incomplete` 与模块交付结论的独立性。

**停止条件**：同一实现确定性失败达到修复预算、同一用例达到两轮，或存在未分类/未完成 checkpoint 时停止页面试错并转技术复核；不能以“已完成目录”、截图、汇总通过数或平台跨应用缺口强行收口。

### 场景 AI：页面更新通过审计后反向更新测试用例

**触发**：页面发布或页面合同发生变化，且页面 Probe/运行时审计取得了当前路由、控件、字段、弹窗、按钮状态、API 操作和 UI/API 终态证据。该场景回答“页面已经更新并通过审计，如何反向更新正式用例”。

**标准闭环**：

1. 记录页面更新前后观测、应用版本/环境/角色/语言/路由、采集时间和证据文件哈希；
2. 执行 `probe → diff`，确认是 clean diff、技术变化还是业务语义变化；
3. 将页面证据转换为 runtime-audit V2 校正合同，按 `sourceIds`/`caseId` 精确找出影响集，不按标题或整套路由盲目扩散；
4. 对每条受影响用例生成机器决策：`no-change`、`correct-case`、`add-case`、`delete-case`、`split-case`、`merge-cases` 或 `block-case`；
5. 在自动策略允许且证据完整时，同步更新正式用例的路由、capability、字段/控件身份、Claim、验证信号、断言 surface、覆盖 ID、技术绑定、Recipe 和实现指纹，并保存 before/after 指纹及变更原因；
6. 若页面变化改变业务前置、步骤、预期、精确提示、规则或数据语义，不能只更新技术绑定：必须同时登记 `businessRuleChanges`，进入人工规则确认或人工异常队列；
7. 更新完成后重新生成执行意图和增量选择，取得执行授权，先做静态合同/局部测试，再定向重跑影响用例；新标准收据被接受后，才更新当前状态和索引。

**不得反向更新的情况**：证据未登记/过期/哈希不符、上下文不一致、来源与运行事实冲突、API operationKey 冲突、写请求或清理证据不完整、页面 Diff 不能稳定定位字段，或超出 `autoApprovalPolicy`。此时只生成提案并标记 `review-required/block-case`，不得自动改正式用例或把页面事实写成产品规则。

**结果与影响**：

- 仅技术定位变化：旧业务语义不变，但实现指纹变化使受影响旧收据进入待重验；只重跑影响集。
- 业务语义变化：旧用例指纹和旧收据失效，必须人工确认规则并重跑；不能以页面截图直接判通过。
- `no-change`：不修改正式用例、不失效历史结果。
- `add/delete/split/merge`：同步 canonical 正文、绑定、执行计划、运行账本和索引，保留原始来源与变更审计链；删除不等于静默丢弃历史。

### 场景 AJ：运行收据反向生成审计校正合同

**触发**：一次标准运行产生完整或部分 execution receipt，且需要把实际观察反馈给测试方案治理层。

**流程**：读取同一 `runId` 的 operation、assertion、context guard、API/UI、cleanup 收据 → 校验 `caseId`、用例指纹、实现指纹和执行上下文 → 生成 runtime-audit V2 校正合同 → 标记 `no-change/correct-case/add-case/delete-case/split-case/merge-cases/block-case`。

**可反向更新范围**：在策略允许时，可更新路由、能力调用、数据/清理配置、断言落点和实际操作轨迹，并生成 `provisional` Recipe 精化候选；不得直接覆盖正式业务语义、PRD、正式业务规则或测试意图。正式规则变化仍需批准来源或人工评审。

**阻断**：收据不完整、Claim/operation 缺失、指纹或上下文不匹配、写入无操作收据、清理证据不足时，只生成诊断或人工异常，不得反向改用例，也不能据此判定 `passed`。

### 场景 AK：失败反馈反向生成失败分析与修复提案

**触发**：业务运行失败、页面 Diff 失败、清理残留、预检失败或批次 watchdog 中断。

**流程**：仅消费同一 `runId` 的结构化 feedback/evidence、环境/应用指纹、seed/cleanup 阶段和残留结果 → 生成失败分析、归一化分类、根因假设、最小验证和修复 proposal → 按 proposal 指纹审批 → 修改受影响 Page/Flow/adapter/合同 → 运行局部合同测试和受影响用例。

**边界**：异常堆栈、截图或概括性错误文案不能反向推导业务规则、精确提示或产品缺陷；只有稳定 UI/API 终态同时证明预期不成立，才允许生成 `product-defect`。技术/环境失败只更新诊断和修复队列。

### 场景 AL：测试用例与运行证据反向生成 PRD/业务文档

**触发**：历史项目缺少完整 PRD，需要根据已有正式用例、来源 Claim 和运行观察建立产品文档基线。

**流程**：以正式用例和已验证来源为输入，按实体、状态转换、约束、UI/API 观察和清理结果生成 PRD 草稿或章节 → 标记每条内容的来源和证据等级 → 对冲突、推导和未证实规则进入产品确认队列。

**限制**：反向生成的 PRD 是文档候选/历史基线，不是新的业务权威；不能用旧用例或旧运行摘要反向制造不存在的字段、接口、提示或规则，也不能覆盖当前产品确认结果。正式规则仍须来源注册、人工确认和必要重跑。

### 场景 AM：浏览器/发布信号反向生成发布证据与新鲜度结论

**触发**：页面 Probe、浏览器响应和运行环境采集到应用版本、发布信号或稳定性信号。

**流程**：收集当前路由的 browser contract signals 和 release evidence → 去重并关联运行批次、环境、语言、角色和路由 → 计算证据新鲜度、发布变化和可复用性 → 更新 release evidence artifact 与增量影响候选。

**边界**：请求 ID、链路 ID、CloudFront 节点、响应时间或响应长度不能伪装成发布身份；发布身份不可用时本次完整执行仍可通过，但结果只能是 `run-only`，不自动扩展跨发布复用。仅发布信号变化而无业务影响时，不得强制重跑全部用例。

### 场景 AN：业务规则观察反向生成规则账本与覆盖矩阵

**触发**：页面/API/下游运行观察、新的人工确认或规则冲突需要沉淀为可追溯规则资产。

**流程**：按正向、反向、边界、作用域和独立数据变体登记观察 → 生成 rule observation ledger、candidate rules、scenario coverage 和冲突评估 → 关联 `ruleId`、`caseId`、Claim、来源指纹及有效上下文 → 达到策略门槛后进入 `ready-for-human-review`。

**边界**：单次观察只能形成 `observed/provisional` 候选；重复同一数据不增加验证维度；任何反例进入 `conflict`；清理失败或缺少反证不能升级为 `supported`，更不能自动形成跨版本 `formal` 规则。

### 场景 AO：历史运行/旧收据反向迁移为标准收据

**触发**：旧 Allure、旧账本、模块报告或旧业务规则存在，但格式不符合当前标准收据合同。

**流程**：按 `caseId` 和旧指纹定位历史证据 → 尝试补齐 operation、Claim、上下文、API/UI 清理和文件哈希 → 生成旧收据适配任务与迁移 backlog → 只有补录无法证明完整执行时，才转显式重跑审批。

**边界**：迁移只恢复可证明的历史事实，不改变业务语义，不把旧格式静默升级为当前实现证据；无法补证的用例保持 `legacy-passed/evidence-revalidation-required`，不能直接进入当前 `passed`。

## 5. 典型变更场景决策表

| 变更事件 | 是否重跑 | 是否失效旧通过 | 责任分类/动作 |
|---|---|---|---|
| 仅改文档排版、报告说明 | 否 | 否 | 结果不变 |
| 改前置/步骤/预期/Claim | 受影响用例 | 是，待新收据 | 增量审计与批准 |
| 改精确提示或按钮提交语义 | 是 | 是 | UI 运行证据校正后重验 |
| 改 locator/handler/page/API/清理 | 受影响用例 | 是 | automation-gap 或 revalidation |
| 业务规则人工确认改变语义 | 是 | 是 | 更新规则、绑定、计划并重跑 |
| 仅发布身份不可采集 | 否（若其他证据完整） | 本次不失效 | `run-only`，限制自动复用 |
| 网络抖动/连接重置 | 最多有界恢复 | 否 | 瞬时平台/环境故障 |
| C 端/行业商品/终端不可用 | 否 | 不适用 | `deferred/external-dependency` |
| 稳定 UI/API 终态与预期矛盾 | 是（修复后） | 是 | `product-defect` |
| 历史报告缺新版收据 | 先协调 | 不自动失效为失败 | 适配旧收据，必要时审批重跑 |

## 6. 报告与验收应回答的固定问题

每次流程结束，报告至少逐 `caseId` 回答：

1. 来源、用例、规则、绑定、实现和上下文指纹是什么？
2. 本次是否实际执行，是否具备逐 Claim、operation、guard、cleanup 收据？
3. UI、API、下游、清理各自的观察结果和权威是什么？
4. 当前状态是通过、失败、延期、阻断、待重验还是仅历史？责任归属是什么？
5. 是否创建对象，服务端 ID 和 UI/API 残留是否为零？
6. 是否触发后续重跑、修复、人工确认或索引刷新？既有通过结果是复用、失效还是不变？
7. 本结论属于商品中心模块交付，还是平台跨系统成熟度？两者不能混写。

## 7. 当前建议（按项目合同格式）

### 必须：先补齐当前闭环的逐用例证据缺口

**目的**：解决参考基线中仍有缺失标准收据的用例，避免用汇总通过数或旧报告授权通过。  
**预期结果**：完成证据协调；无法证明完整执行的用例进入明确重跑审批；`caseId + 指纹 + 清理证据` 可逐条对账。  
**后续影响**：只影响缺口用例；已有完整当前收据的通过结果不重跑，平台成熟度仍可能因跨应用门禁保持未完成。

### 必须：业务规则/方案变更统一走“审计→影响集→批准→增量执行”

**目的**：防止人工改文案后旧收据继续冒充当前通过。  
**预期结果**：每次语义变化生成可追溯事件、受影响 `caseId` 和新收据。  
**后续影响**：仅重验受影响用例，增加规则确认和局部执行成本；不重新打开无影响的已通过用例。

### 暂不建议：在未满足恢复条件前启动跨应用试点或全量重跑商品中心

**目的**：当前跨应用试点明确为用户显式启动且已有阻断登记。  
**预期结果**：保持平台 `deferred/incomplete`，不制造新的无效运行证据。  
**后续影响**：不影响商品中心模块独立交付；只有在提供真实目标系统并完成适配器后再定向启动平台试点。
