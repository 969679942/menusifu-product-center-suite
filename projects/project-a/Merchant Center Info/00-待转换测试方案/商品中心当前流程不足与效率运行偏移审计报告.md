# 商品中心当前流程不足、低效与运行偏移审计报告

> 审计日期：2026-09-01  
> 审计范围：仅商品中心当前应用（`applicationId=merchant-center`）；排除跨应用、跨系统真实试点。  
> 产物类型：`generated-evidence`。本次不修改 `public-core`、`project-adapter` 或 `domain-asset`，不重跑业务用例；仅执行静态、合同、索引、产物和治理审计。

## 1. 结论先行

当前流程不是“没有能力”，而是存在明显的“能发现问题，但不能快速、稳定闭合问题”的结构性不足：

1. 页面合同已经发现当前版本偏移，但 44 条 Diff 发现仍停在 `review-required`，没有自动闭合到批准绑定和受影响用例重验。
2. 资产索引检查失败，已完成/未落地索引过期；这会使流程分母、绑定状态和报告状态存在不同步风险。
3. 维护性门禁失败：232 个受审文件中有 4 个高优先级大文件（基线允许 3 个），128 个直接身份模板已达到上限，说明新增场景仍在增加维护成本。
4. 技术绑定审批请求 11 条全部 `pending`，页面观测到的能力不能进入正式执行链，形成审批积压。
5. 当前业务结果可执行，但复用性较弱：落地审计显示组模块 117 条为 `run-only`，商品模块只有 1 条当前 `passed`，其余大量处于 `ready/handled`，说明“历史有结果”与“当前可复用”之间存在断层。
6. 迁移闭环未完成（1 个未归属文件、1 个桥接违规、14 个清单变更），导致 readiness 刷新在生命周期预检阶段直接阻断。
7. 来源治理仍阻断 20 条当前目标用例；这不是测试执行失败，但会持续阻塞生成和自动化晋级。

因此，当前最重要的不是继续扩大执行量，而是先解决“索引—页面合同—绑定审批—收据复用—迁移门禁”这条治理链的闭合问题。

## 3. 当前流程不足

### P0：索引和治理事实不同步

**证据**：`ui-cases:check` 明确报出 `已完成/index.json`、`已完成/index.md`、`未落地/index.json`、`未落地/index.md` 过期；当前索引显示 420/191，但检查认为派生资产不是最新。

**影响**：负责人可能看到旧的绑定数量、旧的未落地原因或旧状态；执行计划、运行账本和索引无法保证同一时间点对账。状态裁决的正确性会受到“消费旧索引”的间接影响。

**根因判断**：当前流程把索引刷新放在变更完成后，但缺少强制的“任何正式用例/绑定/决策/收据变化后自动刷新并阻止消费旧索引”的统一入口；同时存在多条项目专用命令，容易绕过刷新。

**最小改进**：建立单一治理收口命令，先校验来源/绑定/收据，再原子刷新四份索引；索引指纹与消费命令绑定，过期即阻断，不允许人工修改索引。

### P0：页面偏移发现后闭环断在 Diff/审批层

**证据**：页面合同 Diff 为 `review-required`，共 44 条发现：`RELEASE_EVIDENCE_STALE=11`、`RELEASE_FINGERPRINT_MISMATCH=22`、`ROUTE_FINGERPRINT_MISMATCH=11`；技术绑定审批请求 11 条全部 `pending`、批准 0。

**影响**：流程能够识别页面/发布变化，但不能自动完成“影响用例→绑定更新→增量执行→新收据→状态刷新”；当前会长期停留在候选或人工审批队列，运行偏移不会及时闭合。

**根因判断**：页面变化、发布证据、技术绑定审批和执行计划是分开的入口，没有一个项目级编排器保证 Diff finding 必须有 disposition、owner、截止状态和后续选择集。

**最小改进**：为每个 finding 强制生成 `findingId → caseIds → disposition → approval → impacted plan → receipt` 链；无 disposition 的 finding 不得被报告为“已处理”。

### P0：迁移门禁阻断 readiness，但问题责任不够可见

**证据**：迁移闭环 `status=incomplete`，扫描 131,564 个文件，存在 `unowned=1`、`bridgeViolations=1`、`inventoryChanged=14`；`build:system-test:readiness` 在预检阶段失败，错误为 `PROJECT_MIGRATION_NOT_COMPLETE`。

**影响**：即使商品中心业务合同和类型检查通过，项目 readiness、评审队列和最终裁决也无法刷新；使用者容易误以为是业务用例失败，或反复执行同一 readiness 命令而没有新进展。

**根因判断**：迁移状态、业务交付状态、平台 readiness 没有在用户界面/报告中形成足够清晰的分层摘要；未归属文件和桥接违规没有直接显示文件级责任人和修复建议。

**最小改进**：输出按文件分组的迁移阻断报告，明确 `public-core/project-adapter/domain-asset/generated-evidence/history/transient` 归属、责任人、修复动作和验收命令；迁移未完成时只更新迁移报告，不重复刷新其他派生状态。

### P1：当前通过、历史通过和可复用结果混在使用体验中

**证据**：落地审计结果：商品模块 216 条中 `passed=1`、`ready=187`、`handled=12`、`runOnly=1`；组模块 144 条中 `passed=117`，但 `runOnly=117`，整体均为 `incomplete`。

**影响**：用户可能把历史通过误解为当前可复用通过，或把 `ready` 误解为已执行；发布身份缺失、证据不完整和当前状态之间的差异不够直观，容易造成不必要重跑或错误放行。

**最小改进**：报告首页固定分开展示 `formalDisposition`、`executionStatus`、`evidenceStatus`、`reuseStatus`、`verificationStatus`、`actionRequired`；禁止只展示一个最终字符串。

### P1：来源阻断规模较大，生成链路缺少降噪和优先级闭环

**证据**：unsupported-source 审计识别 202 条对象，其中 20 条 `currentGoalBlocking=true`；来源策略明确禁止自动化脚本、Page/Flow/Recipe 和未结构化运行证据作为正式来源。

**影响**：生成产品就绪度长期被来源问题拖住；但当前报告只能看到阻断数量，不能快速知道每条缺口需要补 PRD、XMind、BR 还是产品确认。

**最小改进**：将来源阻断按“缺精确来源/来源废弃/XMind 节点不唯一/需产品规则确认”生成责任队列和最小补件模板；补件后自动只重审受影响 caseId。

### P1：运行计划与 checkpoint 的选择集元数据存在缺口风险

**证据**：当前 2026-09-01 的多个优化计划含完整 `selectionFingerprint` 和大选择集（例如 200、333、337 条），但部分批次 checkpoint 的 `selectionFingerprint` 为空，尽管记录了 `planFingerprint`、`selectedCaseIds` 和 `terminalCaseIds`。

**影响**：恢复时可能只能按计划指纹而无法严格确认“同一选择集”；在选择集变化后存在错误复用旧 checkpoint 的风险。

**最小改进**：checkpoint 强制保存并校验 `intentFingerprint + selectionFingerprint + selectedCaseIds + terminalCaseIds + incompleteCaseIds`；缺任一字段直接拒绝恢复，并生成 `selection-metadata-missing` 诊断。

### P1：维护性退化正在转化为执行低效

**证据**：维护性审计扫描 232 个文件，4 个高优先级文件超过 2000 行，超过基线 3 个；直接身份模板 128，达到上限。最大文件包括 6610 行组 runner、2766 行标准商品 flow、2348 行组 page、2082 行调味 page。

**影响**：同一页面/规则修改需要触碰大文件多个区域，增加 locator 漂移、重复逻辑、误影响和审查成本；执行失败后诊断上下文也变大，降低修复速度。

**最小改进**：优先拆分组 runner、标准商品 flow、组 page 和调味 page；将动态身份统一迁移到 `createAuditFieldValue`，按字段 maxlength 分配，禁止继续直接拼接 `Date.now()/timestamp`。

### P2：审批和入口过多，流程选择成本高

**证据**：项目 package scripts 同时存在 intake、contract、Recipe、Gold、group、item、seasoning、source-governed、platform、migration、pipeline 等大量入口；技术绑定、业务规则、合同发布和平台发布又各有独立审批文件。

**影响**：使用者难以判断先执行哪个命令，容易出现只跑局部生成、只跑局部审计、跳过索引刷新或重复运行已通过批次的情况。

**最小改进**：提供一个只读 `doctor/status` 命令，输入变更类型后输出唯一推荐路径、前置门禁、禁止命令和预计影响；旧入口保留兼容导出但不再拥有独立状态机。

### P2：报告-only 与业务结果隔离虽有规则，但缺少统一可视化摘要

**证据**：公共规则要求 synthetic/isolated result directory；当前多个报告、Allure、迁移和合同产物并存，用户需要跨目录理解其用途。

**影响**：流程验证、业务执行、历史证据迁移和平台 readiness 容易被混在同一报告中，造成误判。

**最小改进**：所有报告强制显示 `scope=report-only|business-execution|platform-governance`、是否改变业务状态、是否可授权 `passed`，并在聚合页分栏展示。

### P1：页面 Probe/发布事件尚未形成稳定的自动触发器

**证据**：流程文档将主动触发成熟度评为“较成熟”，明确仍需在 CI 发布事件中统一调用 Probe，避免只依赖人工启动命令；当前页面 Diff 虽已生成，但没有证据表明每次发布都自动触发并绑定同一 pipeline runId。

**影响**：页面更新可能先于审计被发现，窗口期内旧 locator、旧断言和旧发布证据仍可能被使用；问题发现依赖人工记得执行 Probe，存在漏检。

**最小改进**：将发布事件、页面 Probe、Diff、影响集和增量计划串成幂等 webhook/job；记录 release event id，重复事件不重复生成计划，失败事件进入可见重试队列。

### P1：Finding/审批没有明确的时限、责任人和超期升级

**证据**：当前技术绑定审批请求 11 条全部 `pending`，页面 Diff 44 条均有阻断发现；现有产物包含候选和审批状态，但未见统一 SLA、owner、到期升级和撤回/重新打开规则。

**影响**：偏移可能长期停留在 `review-required`，执行团队无法区分“等待业务确认”和“等待技术修复”，也无法量化治理吞吐量。

**最小改进**：每个 finding、来源阻断、技术绑定和规则候选必须有 owner、dueAt、blockedBy、nextAction、escalation；超期只升级治理状态，不自动放行或自动重跑。

### P1：计划粒度与实际批次粒度差异过大，存在低效和误恢复风险

**证据**：同一日期存在 200/333/337 条的大选择集计划，而实际 checkpoint 只覆盖 3 条或 5 条；部分 checkpoint 缺少 `selectionFingerprint`。这不必然是业务错误，但说明“计划—批次—checkpoint”粒度和命名尚未统一。

**影响**：计划阅读、预算评估和恢复判断成本高；执行人员可能误把 sentinel/repair 小批次当成完整计划，或在不同计划间复用错误 checkpoint。

**最小改进**：强制一计划一 `planId`、一选择集一 fingerprint、一批次一明确子集；报告显示父子关系、覆盖比例、未执行数量和恢复入口，缺元数据直接阻断恢复。

### P2：生成证据规模过大，静态审计本身存在性能成本

**证据**：迁移审计扫描 131,564 个文件，其中 127,705 个为 generated-evidence；当前项目同时维护大量历史、瞬态、Allure、Playwright 和中间产物。

**影响**：迁移、索引和质量命令耗时增长，AI 诊断容易被历史噪声淹没；重复扫描也会增加输入指纹漂移和误报概率。

**最小改进**：按 manifest/索引先做增量文件集合计算，历史和瞬态只按哈希清单核验；禁止为单条 case 诊断递归扫描全量 output/allure/test-results。

## 5. 执行方案（下一阶段）

### 阶段 1：治理事实收口（必须）

**目的**：先消除索引过期、迁移阻断和 checkpoint 元数据缺口，保证后续分析使用同一事实源。  
**动作**：定位 1 个未归属文件和 1 个桥接违规；核对 14 个迁移变更；补齐 checkpoint selection fingerprint；重新运行迁移审计和索引 check。  
**预期结果**：`ui-cases:check`、迁移 closure 和 readiness 预检不再因旧派生状态或缺元数据阻断。  
**后续影响**：不重跑业务用例；只刷新治理产物。若发现业务资产真实变化，再生成受影响 caseId，不扩散为全量重跑。

### 阶段 2：页面偏移闭环（必须）

**目的**：把当前 44 条页面 Diff 从“发现”推进到“逐 finding 可处置”。  
**动作**：按 finding 生成 owner/disposition；区分证据过期、路由变化、发布身份变化和业务语义变化；重新生成技术绑定候选和影响集。  
**预期结果**：11 条 pending 绑定审批逐条有批准/拒绝/延期结论；受影响用例有增量计划，未受影响用例保持不变。  
**后续影响**：可能使受影响旧收据进入待重验；不重跑无影响的已通过用例。

### 阶段 3：复用率和收据闭环（必须）

**目的**：减少 `run-only/ready/handled` 与当前 `passed` 之间的断层。  
**动作**：先做历史证据协调，再补发布/上下文/清理收据；协调失败的用例才进入显式重跑审批。  
**预期结果**：逐 `caseId` 明确 `reusable`、`run-only`、`invalidated`，不再用汇总通过数授权当前通过。  
**后续影响**：已有完整当前收据的用例不重跑；只有无法证明完整执行的用例进入审批。

### 阶段 4：降低维护成本（必须）

**目的**：解除高优先级大文件门禁并降低运行偏移的修复成本。  
**动作**：拆分 4 个热点；集中身份生成；补模块无关合同测试；再运行 typecheck、architecture、capability 和 maintainability。  
**预期结果**：高优先级文件不超过基线，直接身份模板下降，页面/Flow/数据工厂边界更清晰。  
**后续影响**：实现指纹变化会使受影响业务收据待重验；仅文档变化不触发业务重跑。

### 阶段 5：来源阻断降噪（可选但重要）

**目的**：降低 20 条当前目标来源阻断对生成就绪度的持续影响。  
**动作**：按责任人生成补件队列，优先处理能补精确 BR/PRD/XMind 的条目；废弃来源和不适用项保持历史追溯。  
**预期结果**：每条阻断都有补件类型、责任人、恢复条件和 caseId 级状态。  
**后续影响**：只重审补件对应的用例；不改变已通过用例。

### 阶段 6：统一入口降复杂度（可选）

**目的**：降低命令选择错误和重复执行。  
**动作**：设计只读 doctor/status 入口，按变更类型输出唯一执行路径和影响预估。  
**预期结果**：用户可以在不启动业务的情况下知道下一步命令、前置门禁、禁止事项和产物位置。  
**后续影响**：只新增公共编排/文档能力，不改变业务结果；属于流程效率优化。

## 6. 反向 double check 与遗漏结论

本次第二轮检查覆盖了：

- 权威目标、统一入口和资产索引；
- package scripts 的 intake、contract、Recipe、规则、漂移、迁移、pipeline、执行和发布入口；
- 页面合同 Probe/Diff/Impact、运行时审计校正、技术绑定审批；
- 执行计划、选择集指纹、checkpoint、运行收据、清理和状态裁决；
- 来源阻断、业务规则生命周期、历史证据迁移、维护性和能力索引；
- 商品中心模块交付与平台 readiness 的隔离。

**结论**：没有发现新的独立流程类别遗漏；但发现 3 个原报告中没有充分强调的重点：

1. “发现偏移”与“闭合偏移”之间的 finding 责任/审批/计划链不完整；
2. checkpoint 选择集元数据缺口可能破坏安全恢复；
3. 多入口造成低效和误操作风险，需要只读统一状态入口。

这表示当前主要问题不是缺少更多测试命令，而是治理链闭合、复用资格清晰度和入口复杂度。

## 7. 接下来的重点排序
