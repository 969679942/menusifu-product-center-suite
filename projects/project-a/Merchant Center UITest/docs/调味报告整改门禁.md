# 调味报告整改门禁

本文件记录调味方案本轮报告与防假通过整改的执行口径。它是项目流程说明；公共运行时、收据合同和状态裁决仍归 `D:/Menusifu/Test Automation Platform`。

## 通过条件

- Allure 只展示中文业务步骤，并按商品中心、调味管理、品牌调味/调味模板/下发记录/门店调味分层。
- 每个展示步骤必须同时具备中文业务/诊断标题和最终状态；原始 `Fill`、`Expect`、`locator`、未解析占位符或无状态步骤均使报告审计失败。
- 业务证据、运行收据和失败诊断必须通过公共步骤附件合同绑定到产生证据的明确步骤；根级附件或顶层附件专用节点属于未绑定证据。框架自动失败截图优先绑定最深层失败断言步骤，无法定位时才归入中文 `失败诊断：` 步骤；附件不得因此生成业务操作收据。
- 每条正式用例都必须有当前用例指纹、实现指纹、前置和断言收据、至少一个真实执行操作收据、清理证据。
- 任一断言出现 `observed-mismatch`、断言收据缺失、操作收据缺失或清理非零残留，状态只能是 `failed`、`ready` 或相应阻断状态。
- 标题描述写入行为的用例必须执行对应 UI 操作和保存后回读；只读取列表、控件可见性或接口静态合同不能覆盖该用例。
- 失败用例至少保留失败分类、失败步骤、错误上下文、运行证据、失败截图和 trace（按运行配置）。

## 执行顺序

1. 运行非业务 Allure/执行收据合同测试。
2. 运行调味绑定覆盖审计，确认标题动作族与 capability/assertion 一致。
3. 对已有结果运行 Allure 完整性审计；若出现 `PASSED_WITH_INCOMPLETE_BINDING`、`MISSING_BUSINESS_OPERATION_STEP`、`TECHNICAL_STEP_TITLE`、`MISSING_STEP_STATUS` 或 `ATTACHMENT_NOT_BOUND_TO_STEP`，旧报告只能标记为历史证据。
4. 仅批准受实现指纹或用例指纹影响的调味用例重跑。
5. 生成 Allure 报告后检查失败步骤、期望/实际证据、附件和清理结果。
6. 通过公共平台门禁后，才能把当前收据写入正式账本。

报告完整性审计命令：

```text
npm run audit:seasoning:report -- --results=<独立 runId/allure-results> --recipes=systems/merchant-center-product-center-seasoning/recipes.json --output=output/system-test/merchant-center-product-center-seasoning/seasoning-allure-report-audit.json
```

审计报告中的 `passedCases` 只是原始 Allure 状态；只有 `status=pass` 且 `findings=0` 才能进入当前结果评审。`incompletePassedCases` 不得计入当前通过数。

## 禁止事项

- 不把 Playwright 全绿、接口返回 2xx、截图或静态页面非空当作业务通过。
- 不把人工确认或历史 Allure 结果当作当前执行收据。
- 不为验证报告格式重跑商品、组或其他已暂停方案。
- 不把“全绿但缺少业务操作步骤”的历史报告重新生成后当作当前通过；必须先完成绑定整改并取得新的执行收据。
