# 商品中心自动化实施计划

生成日期：2026-07-21

## 当前基线

- API：两份 OpenAPI 3.1，共 656 个 operations、1006 个 schemas；一份 Postman 集合含 10 个实际请求样例和认证材料。
- 资料：60 份 Markdown、9 份 XMind；手工/正式用例与自动化候选并非完全一一对应。
- UI：Playwright + TypeScript 可编译，可识别 53 条测试，当前主要覆盖商品列表、商品创建和导航冒烟。
- 审计：34/34 路由、221/221 控件、82 个 overlay、20 个二级 overlay、222 个字段已有功能审计证据。

## 事实源优先级

1. 真实 UI 行为与实际 API 请求/响应。
2. 可复现的直接 API 探测。
3. OpenAPI schema 与约束。
4. 已确认 PRD、产品确认记录、正式测试用例。
5. B 端设计规范与 BR 追溯。
6. XMind 历史方案。
7. 无独立证据的 AI 推导业务规则。

冲突统一进入 `unresolved-rules.json`，无来源或未确认规则不得生成自动化断言。

## P0：基础治理与五实体试点

1. **安全与版本基线**：迁移账号、密码、Token、Cookie、API Key；创建环境变量模板、敏感扫描和 Git 基线。
2. **API 规范化**：保留 OpenAPI 3.1，生成 operation catalog、请求/响应 schema、认证流、脱敏样例、TypeScript 类型和 typed client。
3. **统一黑盒契约**：创建 `black-box-test-contract-builder` Skill 和 `product-center-test-contract.json` JSON Schema。
4. **UI 契约抽取**：生成 routes、controls、locators、fields、validations、dialog-flows 和 UI/API mappings。
5. **规则自动探测**：执行空值、字符、长度、格式、重复、关联和删除矩阵；无法证明的语义规则进入 unresolved。
6. **五实体试点**：分类、做法组、原料、配方/BOM、品牌调味完成 API + UI CRUD、双重验证和零残留。

### P0 验收

- 656 个 OpenAPI operations 全部进入 catalog，operationKey 无重复。
- 34/34 路由具有 locator contract；221/221 控件、82+20 弹层和 222 字段均有证据或明确 unresolved。
- 五实体契约完整率 100%，自动化连续运行两轮无数据残留。
- 认证材料只存在于被忽略的本地密钥区或运行时环境，生成物敏感信息命中为 0。

## P1：主要业务模块

按依赖顺序扩展：

1. 多语言、分类、规格、排序、口味、做法、加料、套餐组。
2. 标准商品、套餐商品、配菜/加料、导入、复制、启停、批量操作。
3. 调味、调味模板、下发记录。
4. 描述标签、商品角标、统计标签、图片、原料、配方、打印档口。
5. 菜单、菜单下发、门店菜单、门店商品、库存、税种、门店配方和打印档口。

每个模块统一执行：资料归一化 → 契约抽取 → 冲突检查 → API 适配 → UI 定位器 → 数据工厂 → cleanup → 生成测试 → 运行验证 → 追溯回填。

## P2：状态矩阵与规模化

1. 覆盖空、加载、错误、分页、页大小、首中末行、启停、发布、下发、门店、渠道、角色和语言状态。
2. 覆盖上传、导入、导出、下载、新窗口、二次确认和影响预检。
3. 建立 API 契约漂移、UI locator 漂移、checkpoint、失败重跑和高风险实体残留扫描。
4. API 负责前置造数和清理，UI 只验证关键用户链路，降低总执行时间。
5. 建立 Allure 报告、覆盖矩阵和 unresolved 规则趋势。

## 最终采集齐全门禁

- 路由 34/34；控件 221/221；弹层 82 + 20；字段 222/222。
- 所有适用必填项具备 UI marker、空提交、前端结果和后端响应。
- 所有适用 CRUD 实体完成 create/verify/edit/verify/delete/verify。
- PRD/BR/TC → contract → API/UI test → 执行结果可双向追溯。
- 状态矩阵适用项 100% 具有 passed、blocked 或 not-applicable 证据，禁止 0/0 通过。
- 测试数据残留为 0，最终产物中的密码、Token、Cookie、API Key、storage state 为 0。

## 执行顺序

1. P0-1 安全与版本基线。
2. P0-2 OpenAPI/Postman 规范化。
3. 创建 Skill 与统一契约 Schema。
4. 导入既有功能审计证据。
5. 完成 34 路由 UI 字段和定位器抽取。
6. 完成五实体 UI/API 差分映射与规则探测。
7. 生成五实体 API + UI 自动化并连续运行两轮。
8. P0 通过后进入 P1，P1 通过后进入 P2。

## 最终目标完成后的后置整改任务

1. **统一测试用例命名规范**：在“最终采集齐全门禁”全部通过后启动，不抢占当前 P0/P1/P2 收口工作。
2. 统一用例编号结构、模块缩写、场景类型、动作对象和预期结果的命名规则，并明确已废弃、替代、阻断用例的命名与状态表达。
3. 建立旧名称到新名称的映射，保证 PRD/BR/TC、Recipe、运行证据和历史报告的追溯关系不丢失。
4. 先输出命名规范和迁移清单供负责人审批；未获批准不得批量重命名现有用例或修改业务内容。
5. 验收标准：新增用例命名检查门禁、存量命名违规清零、所有重命名均有可审计映射，且主集合与 gold set 回归保持通过。
